# Crew 产品演进

更新：2026-10-25（Asia/Tokyo）。工作分支：`codex/product-evolution`。

## 产品责任

本轮用户要求产品负责人主动观察使用过程、发现未被提出的需求、研究成熟交互、判断方向与优先级，并负责实施和验收。用户明确纠正「不是修复」。用户举出的几个问题是观察的起点，不能充当完整需求清单。

Crew 应成为用户日常干活的主要工作台：自然地讨论与交代事情，随时插话和改变方向，查看实际产物、预览运行效果、判断交付并继续修改。用户能够省心地管理持续工作的 AI 团队，完整工作过程尽量在 Crew 内闭环。普通讨论、持续负责某个领域、Git 管理与目标交付都是合理工作形态，不把所有交流强行变成目标。

用户最新澄清（2026-10-25，覆盖上一条入口选择）：如果 Crew 的使用体验能够代替 VS Code / Codex，就只需要在 Crew 中干活。此前选择“VS Code / Codex，会话与 Crew 配合使用”不能解释为希望长期依赖原工具。后续观察主线为“哪些日常工作环节仍迫使用户离开 Crew、为什么”，接续现有会话是现状能力和过渡路径。

随后用户进一步明确：目前不需要自己看代码，完全交给 AI 编写。代码审阅、工程实现与验证由 AI 团队负责，不能把人类代码审阅列为主要使用流程。用户侧主线是看实际成果、体验行为、表达问题和要求，再体验修订效果。

负责人每轮从用户完整流程出发，提出值得改善的体验和取舍，在现有应用里落地持续能力，再独立走查。研究资料、模型建议和绿色测试是判断依据；最终仍要检验用户能否完成自己的事。

目前判断：最影响可信度的是底层工作逻辑，包括讨论与执行的边界、真实执行状态、目标与交付版本、验证证据的来源；最限制 Crew 成为主要工作台的是成果预览与反馈闭环。先保证工作逻辑可靠，再把体验闭环做顺，并沿同一真实使用流程一起验收。完整数据库或新布局都不能单独替代这项工作。

## 研究与证据

本轮读取了「了解 Crew 超大更新」「排查股市预警产出读取问题」「评估 MIB 工程 Crew 更新需求」「精简对话框并协调并行修改」等项目对话。反复出现的用户期待包括：自己检查每一步交互；保留现有导航和关系树；普通问答直接交流；资料按需打开；工作与成果可以持续接续；完成声明须有实际依据。历史 AI 的“已完成”没有直接视作本轮验收事实。

产品基线为 `b159fc5`。已有确认以 [目标交付设计](GOAL_DELIVERY_REDESIGN.md) 为准；较旧的页面说明和测试可能滞后。其他工作树和正式桌面版本各自核查，不能用本分支旧代码推断最新版本仍有同样的问题。

2026-10-25 已完成的观察：

- 在正在使用的 Crew 桌面里走查“负责人总会话 → 任务清单 → 已结束目标 → 交付与文档”。只做导航，未发送消息、改变设置或启动工作。
- 使用现有真实 renderer 与内存 HTTP 夹具，重现同一流程；夹具包含推进中、等待用户、已交付三个目标，未连接真实模型或正式数据。
- Claude Opus 5.5 独立只读评审后，主控抽查关键代码并结合实机取舍。Opus 没有进行用户测试；其“六个横带”和 JSON 信息过载的部分判断需要结合实际显示条件，未照单采纳。

| 观察 | 证据 | 对用户的影响 |
| --- | --- | --- |
| 任务卡写“有交付报告”，整卡仍只进入任务交流 | 正式界面走查；`goal-ui.js` 的 `cards` 与 `open` 行为；隔离 renderer 重现 | 带着看成果的目的进入，还需猜资料与报告入口 |
| 目标详情没有直接使用报告里已经保存的真实结论 | `goals.validate_report` 保存 `summary`，`goal_api.detail` 原只投影标题、状态等元数据 | 用户看到“本轮结束”后仍要翻报告才能判断实际结果 |
| 无执行元数据的历史已结束目标仍显示“尚未启动”及开始提示 | 正式界面与隔离 renderer 同时观察；`app.js` 的目标头部与提示 | 同一页的状态互相矛盾，用户难以信任自己找对了地方 |
| 暂停任务后，在总会话说“想讨论另一件事”被拒；等待用户时只问进度会恢复推进 | 代码观察后，用真实 HTTP 适配器、独立临时库和假执行进程重现；尚未做双载体实机验证 | 讨论与执行的边界不符合这两种输入的直觉，列入下一轮路由设计 |
| `report_available` 表示有任意历史报告 | `goal_api.card` 查询与报告详情排序 | 有报告不能被解释成当前轮已交付，重开场景必须特别验收 |

真实人工可用性测试尚未进行。隔离截图和点击路径说明的是实现行为，不是人类任务成功率；没有使用“高评分”或“好评如潮”作为已核实的竞品事实。

对话边界的隔离复现结果：目标为 `paused` 时，总会话输入“这个任务先保持暂停，我想讨论另一件事”，返回 HTTP 409，目标保持暂停；目标为 `waiting_user` 时输入“现在到哪一步了？只问一下进度”，返回已启动，目标变为 `running`，需求版本未改变。第二种情况验证的是隐式恢复，没有据此断言每次问进度都会改写需求。

## 借鉴与取舍

- [Linear 的工作对象](https://linear.app/docs/conceptual-model)：以项目与工作项承载持续成果。Crew 保留稳定的人、工作和证据归属，会话作为交流入口。
- [Linear 的项目更新](https://linear.app/docs/initiative-and-project-updates)：进展应帮助人判断健康度、风险和下一步。Crew 不把所有内部消息重新汇总成另一份阅读负担。
- [NN/G 渐进披露](https://www.nngroup.com/articles/progressive-disclosure/)：按照任务重要性安排信息。Crew 主区应先帮助人理解当前工作，详细资料按需展开，既有能力继续可达。
- [NN/G 长等待与中断](https://www.nngroup.com/articles/designing-for-waits-and-interruptions/)：长流程需要历史内容、后台执行和接续支持。Crew 的观察覆盖离开、返回和继续，不只检查首次操作成功。
- [NN/G 用户控制](https://www.nngroup.com/articles/user-control-and-freedom/)：返回、取消和退出应符合人的预期。阅读成果应当可以安全返回，不改变工作执行状态。
- [Claude Desktop](https://code.claude.com/docs/en/desktop)：借鉴在同一工作流程里观察执行、审查变化、追加方向的衔接，不照搬它的权限或会话模型。

Opus 的有效提醒是：人的重点在于判断“值不值得、可信不可信、下一步怎么走”。因此“回来了解进展”必须连接到实际动作，不能以看过摘要为终点。

用户明确主要工作台目标后，下一轮重点研究三段闭环。以下是参考资料与设计假设，尚不代表 Crew 已实现：

用户随后已明确不审代码，下面“文件/差异”模式用于 AI 的工程核查与必要时的深入查看，不作为人类默认工作路径；用户侧优先第二、第三项。

- 成果 → 文件/差异 → 局部反馈 → 修订。借鉴 [Claude 文件操作](https://code.claude.com/docs/en/desktop#open-and-edit-files) 与 [VS Code 改动审阅](https://code.visualstudio.com/docs/agents/run/review-code-edits)。在 Crew 里应能从当前任务找到实际改动，带着文件、范围和版本提出反馈，再比较修订结果，无需复制路径和重新解释。
- 运行结果 → 直接体验 → 指向问题 → 再验证。借鉴 [VS Code 集成浏览器](https://code.visualstudio.com/docs/debugtest/integrated-browser) 与 [Claude 预览](https://code.claude.com/docs/en/desktop#preview-your-app)。先明确当前预览来自哪份工作、哪个版本，再让反馈回到该任务；具体支持范围按实际工作场景决定。
- 随手追问 → 理解原因 → 继续主线。借鉴 [Claude 的上下文侧问](https://code.claude.com/docs/en/desktop#ask-a-side-question-without-derailing-the-session)。Crew 需要明确解释与修改要求的边界：普通追问不意外复工，明确修改形成可持续的任务决定。解释过程中形成的重要决定需要保存，不能照搬临时问答关闭即消失的行为。

这些能力按当前任务展开，保留既有导航、关系树、草稿与阅读位置；先找完整工作流程中的真实缺口，再确定实现范围。

## 演进方向

| 方向 | 人要完成什么 | 当前判断 |
| --- | --- | --- |
| 看懂交付并继续 | 找到成果，看懂结论和局限，打开依据，回到原工作 | 首轮实现与隔离验收完成；合并、发布和部署状态分别核实 |
| 对话与改方向可预测 | 随口追问、纠正、安排下一件事，理解工作是否会继续 | 接下来验证暂停、等待用户、验收后追问等真实情景，再确定路由取舍 |
| 在 Crew 内体验成果并反馈 | 围绕当前任务打开实际产物、体验运行效果、直接指出问题、比较修订结果 | 用户不需要看代码；下一轮以成果预览与反馈闭环为优先，代码检查交给 AI |
| 工作持续可接续 | 离开再回来，仍能找到同一工作、重要变化和下一步 | 与稳定存储、工作区身份及版本更新的在建工作衔接；原工具接续作为现状兼容路径，不替代 Crew 自身的工作体验 |

这些方向覆盖整段工作体验；每轮只选能独立交付、可验证的范围。优先级可以随新证据变化，不能为了守住计划而忽略真实体验。

## 下一轮提案：体验成果、指出问题、再验证

主控已抽查的现状：`web.py` 的通用文件接口能够读取源码，但“打开源码”交给 `vscode://file/`；HTML 等普通产物归为外部打开。`git_view.commit_detail` 使用 `git show --numstat` 返回文件与增删统计，尚不是逐行差异。专用交付报告已有独立预览路径，不能因此泛称 Crew 没有预览能力。

此前主控建议优先贯通代码差异与局部反馈；用户已明确当前不需要看代码，该优先建议撤回。现有代码接口盘点保留为技术基础，不作为要求人类审代码的理由。

建议优先贯通：提出目标 → 在 Crew 打开实际成果或运行效果 → 指出页面、产物或行为哪里不对 → AI 修改并自行验证 → 用户回到同一成果再次体验。反馈自动保留所属任务、产物版本以及必要的截图或位置，不要求用户复制路径、解释实现或审查代码。主区按当前操作切换对话与成果预览，既有导航和人员树保持稳定，详细记录按需展开。

验收以用户动作衡量：在 Crew 内完成一次真实成果的查看、问题反馈和修订再体验。AI 需独立核对工程变化与实际行为，用户看到的是改了什么效果、还有什么未解决及下一步可操作入口。修改前后的结果必须可区分，不能让旧预览冒充新版本；报告应连接实际产物，不能以阅读报告替代体验成果。

对话的可控性同时是基础门槛：阅读与普通追问不能意外复工，暂停目标后仍能讨论另一件事。该项已有隔离复现，需要独立明确执行与讨论边界，再改路由并做双载体验收。

## 贯穿各轮的交付责任

用户不应反复承担发现明显断点、追问是否真做过、指出一次性处理无法持续的工作。改善这件事需要应用机制与负责人验收共同承担。

现有报告校验已经要求原始验收逐项对应，区分通过、失败、未验证和模拟，限制仅有示意或未全通过时宣称完成；上下文保存原始要求及修订来源。这些机制应继续保留。它们目前主要校验报告结构：证据引用存在且属于本次执行、`actual` 是否确为实测、结论是否由证据支持，仍不能仅靠这些字段获得证明。“上下文已应用”也不代表模型已经理解并遵守。

后续研究重点是让报告关联应用实际收取的执行结果与产物，并把已确认的完整使用旅程持续回归，而不是继续堆提示词或增加一层赞同的 AI。程序负责可核实的来源、状态和归属；产品负责人仍要判断需求、业务结果与真实体验。首轮因此明确标出结论与验证记录的提交来源，不将 AI 自报包装为独立验收。

## 首轮：看懂交付并继续

目标流程：任务清单明确选择“查看交付” → 直接阅读对应报告 → 识别当前/历史轮次、结论与局限 → 返回原任务。直接进入任务交流仍是另一项明确操作。

实施决策：

- 报告投影使用已经保存的结论与验收记录，不新增摘要模型或补写存量数据；缺少信息明确呈现，不编造结果。
- 详情首先展示紧凑的本轮结论和报告中的验收状态；它是 AI 提交的记录，不能冒充独立验收或用户确认。
- 看历史报告时清楚标明所属轮次。重开目标后，旧报告不会成为当前轮结论。
- 显式查看交付才读取 HTML 并打开现有隔离阅读层；普通打开目标仍保持资料按需展开。
- 阅读与返回不发送消息、不启动或恢复执行，保留原任务的草稿与阅读状态。晚到的旧请求不能打开到另一目标。
- 保留三层导航、默认架构总览、关系树、优先级、QQ、Git、待办和原有资料浏览方式。

这一轮使用已有数据与读取边界。新的关注排序、跨设备已读口径、首页落点、对话路由和工作区存储分别根据观察确定，避免把多个未验证的产品假设捆进同一次实现。

验收覆盖有当前报告、只有历史报告、无报告、长结论、失败与未验证记录、读取失败重试、切换目标后旧请求返回，以及宽窄窗口。验证必须检查真实 renderer，并确认打开阅读的模型调用增量为零。

首轮结果（2026-10-25）：

- 已在本分支实现独立“查看交付报告”入口、紧凑的 AI 提交结论、非零验收记录与未解决项提示，以及直接阅读和返回任务。
- 报告按已保存的业务版本确定先后，当前/历史/本轮较早稿均有明确归属；同一目标更新需求或重开时，已打开报告的归属随之更新，保留正文和阅读上下文。
- 阅读层仅阻止被遮住的任务区交互，侧栏和人员树仍可使用；返回后恢复原控件状态。缺少执行元数据时，只有待规划目标提示“尚未启动”。
- 主控独立临时库验收通过：同毫秒与倒退时间下的报告选择、同轮需求更新、读取前后的业务状态不变。
- 主控真实 renderer 复验通过：同轮新稿、需求变更、进入待验收和重开时 iframe 节点及 WindowProxy 保留，新增 load 为 0；键盘不进入被遮住的任务区；阅读不调用发送、启动或派生执行接口。
- 原 `b159fc5` 独立基线：全部网页 JS 测试 122 项通过；交付阅读 smoke 与既有交互 smoke 均由主控复跑通过。后者使用 `--force-device-scale-factor=1` 排除本机 DPI 尺寸误差。
- 原基线的 Python goal 测试运行 131 项，有 12 项既有通知测试夹具错误（`SimpleNamespace.chat` 缺少 `work`），失败清单与改前基线逐项相同。
- 用户批准合并后，整合主干 `e124b56`（桌面源码版本 0.2.7）重新验证：目标测试 131 项、全部网页 JS 126 项、桌面单元测试 124 项全部通过，交付阅读 renderer smoke 通过。原来的 12 项夹具错误已由主干修复，整合后不再豁免这些失败。

这些证据验证本轮接口和交互行为，不代表真实 AI 工作正确率。正式安装版本和真实工作区的应用情况需要独立核实，不能从源码已合并推断已部署；实际运行版本仍需按现场复验。


## 会话发现与接续：2026-10-26

用户提出待收编应扩大范围并分类。现状问题是入口围绕 VS Code CC 活进程，离线历史整批折叠，用户难以从标题与目录判断以前做过的工作；Codex 原生历史和已归档的 Crew 人员缺少统一查阅入口。

本轮将入口升级为会话库：默认当前工作区，明确切换全部已登记工作区；以待接入、团队、历史归档、后台执行划分工作关系，以载体、运行状态和搜索作为独立筛选。用完整主区承载列表与只读预览，辨认后再交给一位 leader；收编保留原生会话，读取历史不导致复工，旧归档不自动成为新 AI 的记忆。

设计参考 [Linear 搜索](https://linear.app/docs/search) 对最近工作与筛选的衔接、[NN/G 识别与回忆](https://www.nngroup.com/articles/recognition-and-recall/) 对可见线索的建议。Crew 的取舍是同时提供标题、目录、载体、原团队与活动时间；按关系分类，不以载体取代任务分类，也不把所有历史文件混入当前待执行工作。实现边界与接口见 [设计第 15 节](DESIGN.md#15-会话库发现辨认与接入2026-10-26)。
