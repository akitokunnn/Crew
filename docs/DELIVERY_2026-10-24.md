## 为什么这样改拍板

原截图把完成进展、技术债、剩余任务和组员排程放进同一道题，用户被迫先理解工程内部状态，才能猜测“继续①②”是什么意思。这类工程排程首先由 leader 自己决定；若真正需要用户测 develop，应登记步骤明确的人工待办。

真正的拍板只留用户需要选择的一件事。新卡片先展示问题和取舍，再放技术背景。选项要能独立阅读，明确选中后会发生什么。旧题不会由程序编造理由或改变含义，而是保留原文，标明缺失，并通知 leader 补写。同题修订保留 ID、审计和答复链路。

旧格式 `crew ask` 为兼容仍可使用，但会提示补全结构，页面也不会把它伪装成清楚的新卡。新守则和 Codex 工具要求提供完整说明。开启信任模式后，已授权目标内的工程取舍由 AI 自行作出，留下理由；不是继续堆给用户。

## 实现中解决的关键问题

- Crew 身份与 Codex 原生 thread ID 分开保存，恢复时核对原 thread；映射缺失明确失败，避免丢历史后悄悄新建。
- Codex 直接持有原生进程，使用进程创建时间和宿主锁识别存活的旧实例，防止服务重启后重复恢复。
- 本机 Codex 的 PowerShell 包装路径实测会把 native hook 的退出码 2 变成 1。本轮改为显式 JSON deny，真实 Codex 回报 `blocked`。hook 异常则停止 Crew 自己的该会话，不能记作成功。
- `turn/start` 接受与实际可中断之间存在时间差；延迟的上一轮通知也可能串进新轮。本轮绑定返回的 turn ID，停止前等待原生 `turn/started`，实际验证了中断和继续。
- 混合组的叫醒、欢迎、拍板回复改用 Crew 消息地址；不把 Codex 名字冒充 Claude 的原生 `SendMessage` 地址。
- 未安装 Claude 或其进程查询失败时，Codex 的恢复、离线通知、叫醒和 Git 结果投递独立依靠原生租约，不再被 Claude 查询阻塞。
- 托管 Claude 和 Codex 都使用自己的 `CREW_HOME` 与 launcher；hooks 同样尊重该环境，避免分支测试误调正式数据目录。
- 待办处理、撤销、审计及通知保持同一事务；版本检查防止覆盖后续状态，撤销会更正过期的通知。
- QQ 按钮绑定实际发送过的题目快照。用户点旧题的 A，不会被静默解释成修改后的 A；引用回复也不回退到其他项目的当前 leader。
- portable 解包目录退出后可能消失，桌面版把后端按内容保存在所选 home，保证 CLI 和守卫入口继续有效。
