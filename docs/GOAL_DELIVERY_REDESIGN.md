# Crew：围绕目标交付的迭代方案

日期：2026-10-25（Asia/Tokyo）。状态：本文记录当前设计约定，尚未改造生产运行机制。已有原型属于历史探索稿；最新侧栏约定以本文为准，不再为展示重做完整原型。

## 目的和完成定义

用户给出尽可能完整的需求，leader 负责理解、协调、实施、验证和最终答复。每个目标有有限的工作轮次和明确终点；团队身份可以长期存在，工作不能靠历史消息无休止地延续。

这次改造必须同时减少无效执行和改善交付。隐藏内部消息、测试数量增加、程序能启动，都不能单独证明有效。

用户已确认的关键要求：

- leader 能直接干活，确有必要才增加成员，并行安排由 leader 判断。
- 普通问答、解释、讨论、进度咨询和小补充直接在对话里说；不为这些内容建目标或生成文档。真正形成执行与交付目标后，才按目标流程收尾。
- 保留“全部”的 leader / 成员架构总览；每个节点都能进入对应人的对话。目标卡在现有组与目标流程中呈现交付进展，“全部”可切换查看目标。
- 本版实施动态上下文，并提供可检查、可纠正的“它记得什么”。
- 成员能直接对话，用户可以直接改变成员任务；leader 和成员工作中都能接收插话并回应。
- 真实目标的最终交付必须包含简单易懂的 HTML、有用的可视化和具体 example；这项要求不扩散成每次回答或阶段变化都出文档。
- 运维以程序持续守护，复杂故障才调用全局唯一的运维 AI；授权它重启服务、暂停异常目标和修复 Crew 本身的 bug。
- 已建立的 leader 与成员都应支持 CC ↔ Codex 切换，保持身份和目标连续。
- 参考 Codex / Claude 桌面的成熟交互，布局由实现者安排。

## 现有功能保留与界面边界（2026-10-25 追加反馈）

用户明确要求按现有 Crew 迭代。原型未画出的功能不代表删除；先前把交付物、成员直聊、记忆检查放进全局左栏的方案已撤回。

界面维持三层：

1. 全局左栏沿用全部、交流区、Git、我的待办、leader 置顶/优先与列表；保留待收编、用量、额度、QQ 状态、我已离开、设置与主题等现有入口和行为。
2. “全部”继续默认展示所有组的架构图，包括每个 leader / 成员的状态和当前工作。节点都可点进对应人的对话，不用新任务卡替换掉这张总览。目标进展作为同页可切换内容。
3. 进入任一组、目标、leader 或成员对话后，右侧基础栏只常驻本组 leader / 成员关系树，显示人员状态与一句当前工作，点击即可切人。目标列表、交付物、上下文不堆在关系树下面。成员直聊是点击成员后的能力，不新增一个全局页面入口。

点开任务卡，主区展示该任务的状态、结论与交流，右侧关系树保持原位。任务头部提供“交付物”“上下文”等少量入口；点击时，在关系树左侧按需展开一层资料抽屉，覆盖主区边缘，不再挤出一个永久第四栏。一次只打开一个抽屉，切换入口就替换抽屉内容；关闭后回到原任务，保留草稿与阅读位置。关系树不承载这些资料列表。

抽屉明确标出所属组 / 目标；切换组或目标时关闭旧抽屉，防止显示旧对象的数据。相同目标内切换对话对象可保留同一份目标资料。复杂 HTML 报告可从抽屉展开到主区阅读，再返回原任务。按需读取和呈现资料，打开任务卡不预展开全部报告、记忆或执行记录，也不因此调用模型。

系统运维仍是跨组的全局入口，沿用桌面顶部管理员位置，不混入某个组的成员。不同组的交付物、记忆、对话与草稿各自对应，不能切组后显示上一个组的数据。

| 既有能力 | 迭代约束 / 回归要求 |
| --- | --- |
| 全部架构图与当前工作状态 | 继续可总览、点击 leader 和任一成员进入本人会话；保留评论与上下文菜单等已有操作 |
| leader 置顶、优先级、排序 | 沿用现有持久化和优先级语义；不是删除旧实现后重做一套 |
| QQ 连接、离开状态和远程对话 | 左下角保留真实状态与错误信息，现有路由和通知规则回归 |
| 交流区、Git、我的待办 | 继续保留现有数据和功能，不被目标首页覆盖 |
| 文档与历史报告 | 保留已有索引和文件；通过组 / 目标入口按需打开资料抽屉，关系树保持独立 |
| 多工作区、草稿、会话切换 | 继续保留，切人和切目标不丢草稿或恢复错会话 |
| 收编、模型/effort、载体切换、信任、中断 | 在原功能上补齐与目标关联，不减少已实现的能力 |
| 搜索、快捷操作、额度、用量、主题与设置 | 沿用现有能力、真实数据与原有设置，不以原型示例覆盖 |

实施方式：复用现有 `renderSidebar`、`renderAll`、`renderRight`、`CrewChat` 和桌面工作区能力。先补目标数据和停止派发约束，再逐项接入新消息协议、上下文和组内界面；保持旧会话可读，按已验证的阶段迁移。动态上下文确实需要调整执行绑定和调度，这部分有实质改动；不因此整体重写 UI、抛弃现有数据库或替换桌面壳。

已有原型曾把人员、目标、交付物和记忆堆在一个右栏，该做法已被用户否决。原型仅保留为历史探索与已有交互参考，不作为当前侧栏布局的实施依据。后续使用文字或小示意确认必要差异，直接在现有产品里迭代。交流区、Git、用量、QQ 设置等成熟页面以当前实现为基线。

## 目标和工作轮次

一个目标保存原始需求、验收标准、负责人、优先级、依赖、当前版本、当前轮次、交付物和状态。用户不必先填写技术任务表。

| 行为 | 约定 |
| --- | --- |
| 普通问答、解释或讨论 | 直接回答，不自动建任务卡，不为回答生成报告或文档 |
| 在目标内补充需求 | 默认补充此目标，保留原话并更新需求版本 |
| 在 leader 总对话提出需求 | 判断补充或独立目标；只有归错会明显影响工作才询问 |
| 达到可验证标准 | leader 交付证据和 HTML 报告，结束本轮 |
| 确需用户亲手验证 | 转待验收并暂停受阻部分；登记人工待办 |
| 多次尝试后仍未达标 | 允许以有证据的未达标结论结束，保留结果和失败原因 |
| 用户报告交付仍有问题 | 在原目标创建后续轮次，旧报告保留，当前结论标明已重开 |
| 用户说“先做 B” | A 在安全位置暂停，资源优先给 B；结束后恢复被此优先安排暂停的 A |
| 用户说“顺便” | leader 判断是否值得并行，不固定扩充团队 |
| 范围外建议 | 记录建议，未经授权不自行开工 |

实现状态应区别：待规划、推进中、暂停中、已暂停、等待用户、待验收、本轮已结束。完成/未达标/取消是轮次结果，不能用进程 idle 替代目标结束。

“暂停目标”覆盖所属执行、成员、待派发动作与内部自动消息。停止首先持久化，之后请求中断；未确认中断时显示暂停中。保留原生会话、文件和日志。用户手动暂停不会被自动恢复覆盖。

不强制用户估算合适预算。可选时间/用量上限与无进展保护并存；没有预算也要抑制重复尝试和消息循环。

优先让一个组完整承接目标，减少职责重叠与不必要的跨组协调。确实跨组时，接下需求的 leader 负责到底，其他组只承担边界清晰的协助；由主责 leader 统一验收、给用户一份最终答复，不让多个 leader 分别转述全过程。

目标结束后成员留在关系树中标为空闲，历史可查；不因为完成任务就自动归档或让人消失。后续优先复用合适的空闲成员，底层进程可按需释放，身份和历史保留。复用时按新目标装载上下文，不能为了复用把旧目标全部历史也带入。

## 动态上下文：本版实施

### 身份与执行分离

leader / 成员的 Crew 身份稳定；原生 CC / Codex 会话属于特定目标和执行代次。一个 leader 同时承担两个目标时，不能把两个目标继续塞进同一个原生长会话。

建议新增 `goal_executions`，以 execution ID 关联 session identity、goal ID、round、generation、runtime、native ID、配置及状态。并发执行按 execution ID 管理进程、日志和输入；现有单 session 的运行时映射作为旧会话兼容层，不能通过反复改一行“当前 native ID”模拟并行。

### 装载内容

| 层次 | 内容 | 更新方式 |
| --- | --- | --- |
| 长期规则 | 用户明确确认的 leader / 项目 / Crew 范围规则、项目约束 | 明确“以后都这样”才晋升长期规则，注明范围和来源 |
| 目标工作记录 | 原始需求、验收标准、决定、可核验事实、失败尝试、剩余问题、交付定位 | 有意义阶段变化时更新，保留历史版本 |
| 当前执行材料 | 最新输入、相关新增结果、需要的文件片段和证据 | 按当前目标按需装载 |

原始用户要求和确认决定优先于摘要。原文与证据可回查，摘要不能覆盖原始约束。未经验证的猜测不能自动变成项目通用事实。不同工作区保持隔离。

不新增一个每条消息都运行的摘要 AI。持久工作记录和检索承担大部分工作，leader 在阶段结束时写一次有效交接。长会话轮换采用显式交接；改变系统提示不等于清空原生历史。

### 基础输入长度与实际用量（核心验收）

用户特别强调：leader 每轮不能反复吞入大量基础废话。实施同时控制常驻提示与原生历史，而不只减少界面消息或新附加文本。

- 基础指令保持最小必要范围：身份、职责、关键约束、授权和必要工具路由。长命令手册、全部工作流、所有技能说明按使用场景检索，不每轮整包附加；必要的项目规则和用户约束继续遵守。
- 当前目标装载原始验收要求、已确认决定和相关新增事实；项目花名册、全组状态、其他目标摘要、整段聊天和全量日志不作为每次默认输入。
- 对已在当前原生上下文中的材料传递必要变更，避免每条消息重发整份同内容快照。引用按来源/版本去重，旧版本和纯确认不占下一轮有效输入。
- 检索有范围与长度上限，优先结论和证据定位，需要时再取对应片段。成员向 leader 汇报交付、阻塞或改变结论的新证据，不整段转发工具输出和聊天流水。
- 为基础指令、工作记录和检索材料分别设置可检查的装载上限；具体阈值依据 CC / Codex 实测校准。超限先去重、移出可检索背景，必要时做有依据的交接，不能静默截掉用户要求、授权或验收标准。
- 原生 resume 的既有历史也计入检查；新增注入变短不代表整个模型输入已经变短。观察历史膨胀，在合适阶段轮换执行上下文，保留可追溯交接。
- 验收分别测量基础指令、工具 schema、目标材料、检索/消息与原生历史的开销。区分 Crew 可控部分、载体必要开销、非缓存输入、缓存读取/写入和输出；拿不到真实 token 时标为估算，不把缓存读取当成零用量，也不把它按未缓存价格计算。
- 用相同任务的首次输入、连续正常轮次和跨目标切换比较真实用量。没有新增证据时，基础装载和无效唤醒不能随着消息流水持续增长；上下文详情按需查看，不为每轮统计额外生成用户文档或启动摘要模型。

例子：成员复测完成，leader 收到“短句仍失败、对应样本/日志位置、验证版本、下一步建议”；需要判断失败原因时再取相关片段，而不是先读完整测试日志、整组聊天和全部历史汇报。

### “它记得什么”

目标详情折叠展示本次实际采用的需求、决定、事实、来源、适用范围和版本。用户可指出错误、标为过期或纠正。修改写成新版本，下次输入或安全执行边界装载；显示尚未应用/已应用，不能把 UI 修改直接冒充模型已读。

每次执行保存 context manifest：采用的条目 ID/版本、来源锚点、检索原因、是否截断及交接代次。纠正原始依据后关联旧摘要过期，禁止旧事实重新进入后续上下文。

例子：声纹目标的“不要 PR，等着”保留为该目标明确约束。切去性能目标不会把声纹日志整段带入；切回声纹仍能看到原始约束。普通一次性纠正只影响当前目标。

### 旧会话迁移

旧历史保留，不自动激活旧任务。新目标直接使用新机制。用户明确说“继续旧任务”时，提取原始需求、已验证结果、当前约束和剩余问题，来源可回查；历史待投递消息不能被原样恢复成待执行工作。

## 消息协议与无效唤醒

消息至少包含 goal ID、round、requirement version、sender/target execution、kind、correlation ID、causation ID、idempotency key、是否需要答复和可执行状态。已接受的用户输入、目标版本变更和运行状态是判定依据。

- 旧目标版本、已结束轮次、已暂停目标的自动消息只存档；不能唤醒模型。
- 收到、已完成、无新变化等确认不要求再次确认。工具回执不自动转为工作指令。
- 阶段结果、确实阻塞和改变结论的新证据才触发必要协调；同一事项合并成一次有效通知。
- 执行前再次核对目标版本和状态。投递、重试和原生接收分别记账，避免超时或服务恢复后重复执行。
- 指令变更后，冲突的旧排程失效；已完成产物仍留档。
- 连续无进展和消息环由程序先识别、限流并保留证据；复杂判断才升级运维 AI。

声纹旧记录揭示了成员消息延迟数小时投递，以及每条 peer wrapper 提示回复的问题。本版须用回放测试证明这些消息不会重新触发模型，而非仅从用户界面折叠掉。

系统“查看进展”读取已有事实并标注时间，不为状态查询逐个叫醒成员。用户主动发给 AI 的对话按真实输入处理，系统状态回执与 AI 本人答复明确区分。

## 成员直聊、忙时插话与载体切换

主区展示所选目标 / 人的交流与任务内容，右侧基础栏只保留本组 leader / 成员关系树。架构总览和右栏都能点击任意人进入本人对话，显示姓名、角色、目标、载体和执行状态；交付物和上下文从相关组 / 目标入口按需打开第二层资料抽屉，关系树保持原位。支持截图、文件引用、可展开工具记录、中断和回到 leader。打开历史、切换页面和编辑草稿不启动模型。

用户直接给成员的明确新指令优先于 leader 的旧安排。任务变更写回目标记录，leader 下次执行读取；涉及其他执行冲突才通知协调，不逐句转发整段私聊。

忙时输入的目标体验：由当前同一个 AI 接话并回应，然后按内容继续或调整；不等当前整个任务结束。UI 仍提供明确中断操作。收到消息、原生接受、实际回应分开显示。

Codex 使用 `turn/steer` 和 expected turn ID；完成/插话竞态和接收未知必须处理，不能盲目重发成第二次指令。CC 必须对安装版本的 stream-json 行为做真实验证；若不能在当前工具边界接受，需要显式保留现场、原生中断并续接的受控路径，不能用前端“收到”冒充即时 AI 回复。两种载体分别通过忙时插话验收才能宣称支持。

已建立的 leader / 成员都支持切换 CC / Codex。切换前预览交接和重读上下文开销，空闲或确认暂停后操作。身份、目标、规则和产物连续；两种载体原生历史各自保留，切换本身不调用模型。目标并发时需明确切换范围，不能让一个目标切换误改另一个正在执行的目标。

## 决策、人工待办与交付报告

需要用户决定时先出现简短提示“这里需要你”，打开后说明背景并讨论，聊清之后才出现完整拍板：要选什么、为什么需要用户、每项后果、推荐及原因。工程细节在授权目标内由 leader 自主解决。

需要用户亲手操作的事登记 todo，包含做什么、在哪如何做、如何验证和阻塞谁。聊天只提示一次；已做/不做可备注和撤销，结果送回对应执行。受阻部分暂停，其余可行工作继续。

真实执行目标的每轮最终报告必须能从目标卡和文档区打开，并保留历史版本。普通对话和阶段性交流优先直接说，不自动产出额外文档。报告失败可重试生成报告，不重新派发已经结束的工程任务；真实目标交付要求的 HTML 缺失则交付尚未齐全。

报告最少包含：

1. 是否达标、实际交付、仍未解决。
2. 原始验收标准逐项对应证据，区分通过、失败、未验证、模拟验证。
3. 至少一个具体输入/操作 → 期望 → 实际 → 结论的 example；适当提供前后对比、时间轴或流程。
4. 文档、文件、commit、PR、分支和真实验证入口；用户要求等待 PR 时遵从。
5. 必要取舍、未解决问题和后续修改入口。
6. 简单投入记录：时间、实际可得用量、角色分配。缺失用量注明，缓存 token 单列，不能冒充准确费用。

默认由结构化结论、example、可视化数据与证据引用生成统一的 HTML，便于校验完整性、减少报告格式本身的模型用量。HTML 易读、可离线查看；示意例子必须标为示意，不能伪造成实测证据。自由生成的 HTML 在受限容器中预览，默认禁用网络及宿主权限；展示文件和报告不得借此执行自动化或唤醒 AI。

例子：声纹“三场景”报告逐项呈现 A 停顿后 B 接话、B 紧接短句、交替后混说。评测 580 条是覆盖量，不能写成 580 条全部正确；364 个工程测试通过也不能代替识别能力验收。

## 全局运维

每个 Crew home 只有一个独立于所有 leader 的运维控制进程，继续使用 OS 锁。程序监测后台、连接、执行状态和消息循环，正常巡检不调用模型也不打扰用户。

运维 AI 由有意义的故障触发，只读必要现场；一个 incident 合并重复告警，记录有限诊断/修复投入。没有新增证据不反复启动分析。正常任务继续；局部故障优先局部处理。

用户明确授权：

- 确认自有后台已退出后重启；尊重维护、退出和用户停止状态。
- 暂停重复派发、消息循环等受影响目标，保留上下文和执行现场。
- 修复 Crew 自身 bug：隔离分支复现、修改、验证、保留 commit，按项目规则 PR / 合并后应用。
- 修复失败保留失败现场和改动；使用可验证的可用版本恢复服务。

修复 worker 不能依赖已故障的 Crew Web / 派发队列才能启动，运维状态和控制通道也应在后台 HTTP 不可用时能访问。修复对象与运维自身更新需分阶段切换，不能边修改运行源码边宣称已经恢复。

全服务重启前保存应恢复的运行目标，恢复时重新核对最新用户意图，只续接此前正在运行且未被后来停止的目标。待用户、待验收、结束和手动暂停均不自动重开。优先安排产生的临时暂停须记录原因，不能误恢复用户暂停。

故障处理结束只给一次简报与 HTML 事故报告：出了什么、影响谁、恢复到哪、修复例子、验证和 commit。普通健康检查保持安静。

## 验收场景

| 场景 | 必须看到的结果 |
| --- | --- |
| 普通问答、讨论或小补充 | 直接回应，不自动建目标、生成 HTML 或另写文档 |
| 不必要的跨组协作 | 由原组完整处理；确有协助时仍只有一个主责 leader 和一份最终交付 |
| 目标结束与后续复用 | 成员仍在关系树里标空闲；复用身份时按新目标装载，不携带无关旧历史 |
| 相同任务多轮输入与目标切换 | 基础装载有长度上限与来源明细；无新证据时不随流水增长；实际输入包含原生历史，缓存等用量分列；必要用户约束没有为缩短输入而丢失 |
| 从“全部”看人和进入对话 | 所有 leader / 成员状态和当前工作可见，任意节点进入本人，不被任务卡取代 |
| 打开任务卡 | 主区展示任务，基础右栏只显示关系树；资料列表与记忆不会全部展开 |
| 查看组内报告或上下文 | 显式点击入口后才打开第二层抽屉，关系树保持原位；一次一个抽屉，关闭保留任务草稿和阅读位置；换组/目标关闭旧资料，不能串内容 |
| 本版新增功能启用前后 | QQ、置顶/优先排序、交流区、Git、待办、多工作区等原能力继续可用 |
| leader 能独自完成小任务 | 不为组织形式启动成员，直接验证并交付带 example 的 HTML |
| 数小时前的成员确认到达 | 记录可查，模型调用增量为零，不给用户转述 |
| 目标结束后旧阻塞/权限通知到达 | 不重开轮次，不恢复旧排程 |
| 运行中暂停目标并立刻重启服务 | 全组停止派发，恢复后仍暂停 |
| 用户在成员运行中补充方向 | 原生实际接收，同一 AI 回应并调整；不伪造 ACK 为答复 |
| 插话与原 turn 完成竞态 | 不丢、不重复、回应归到正确目标和输入 |
| 同 leader 两目标并行 | 原生历史与 manifest 按目标隔离；用户约束不丢失 |
| 修改“它记得什么”中的过期事实 | 新代次不再采用旧事实，来源与应用状态可查 |
| 已有 leader CC→Codex→CC | 身份、目标不变；各端历史可恢复，配置切换不启动工作 |
| 需要真人做或决定 | 一次提示，说明后才拍板；人工操作有具体步骤与验证 |
| 工程测试通过、产品例子失败 | 明确标未达标，报告不把覆盖量或工程测试冒充正确率 |
| 一个目标消息循环 | 局部暂停，合并为一事故，正常目标继续 |
| Crew 后台崩溃 | 独立控制进程保留现场并有限恢复；只有之前运行的目标可续接 |
| 运维修复自身服务 bug | 隔离复现、commit、验证、按项目规则应用；最终一次报告 |
| 报告仅有漂亮图表、缺实际 example | 交付验收失败，不能宣称完成 |
