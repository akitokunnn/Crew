每个任务可以选择我来把关，或者让 AI 在本次授权内自动决定。实现路线不理想时，AI 应主动找依据、做实验和优化。像“落地声纹”这样的任务，不能装一个速度和准确度都不合适的模型就算完成。

我的主要把关点是新框架形成、审美、实际交互体验，以及重要效果取舍。明确的工程工作自行做；重复说明风险、重复验收同一结果和无效汇报都应减少。

我是个人用户。电脑执行，桌面和网页操作同一套 Crew；手机保持轻量，能对话、控制任务、看文档和网页就够了。CC 与 Codex 的原生能力应保留。

## 必做功能

### 工作区与任务

1. 工作区对应项目文件夹，支持普通文件夹，不强制 Git，也不自动 `git init`。
2. 一个任务有主工作区，可以关联其他工作区；关联入口指向同一个任务，避免复制出独立进度。
3. 组织关系为“工作区 → 任务 → 负责 leader → 按需成员”。一个任务有一个整体负责人，载体和执行实例可以变化。
4. 用户直接对话即可形成任务记录。AI 随讨论提炼标题、目标、条件和完成标准；不要求先填任务表。
5. 普通闲聊不自动变成执行授权。需求未清楚时先聊关键问题；需求清楚时开始做。
6. 任务身份稳定，需求、决定、消息、成员、实验、TODO、报告和成果能够回溯到它。换模型、换载体或后台恢复都不新建重复任务。
7. 任务详情由 AI 维护，用户可以查看、修改；并发修改保留用户内容，不能静默覆盖。
8. 不同任务和项目可同时推进。置顶及显示排序不变成跨项目的强制执行优先级。真实资源不足时明确显示等待原因。
9. 同工作区的任务协调文件、接口和整体体验，不覆盖彼此改动。普通改动尽量集中体验，Git 收尾遵循仓库规则。
10. 已有目标、leader 总会话、成员消息和交付资料都有迁移或保留入口；不能只让新建任务工作正常。

任务状态应区分执行、等待用户、手动停止、故障受阻、已完成、归档和垃圾箱等实际含义。成果是否待体验可以独立表达，不要让一个字段承担相互冲突的含义。状态及关联优先在现有模型上演进，具体表结构由源码核对决定。

### 持续执行与协作

1. 把需求、完成标准、已确定条件、执行进度和下一步持久化。一次模型回复结束后，仍有已授权工作就继续调度；全部完成、需要真实用户输入、手动停止或故障受阻时进入相应状态。
2. 调度基于可执行工作和事件，避免定时空唤醒 leader、反复自我汇报、用“继续”消息堆积上下文。
3. leader 优先自己干，确有独立工作才开成员。成员默认偏好 Codex，leader 默认偏好 CC/Opus；leader 可以按难度选择实际可用的模型和 effort。
4. 成员接收相关需求、边界、必要上下文、已有结论和交付标准。不要默认复制全部历史。
5. 用户可直接和任意成员交流。会改变整体任务的指令同步给 leader，保留原话和来源；普通问答不强制重复播报。
6. leader 可以私聊，协调共享文件、依赖和跨项目工作。沟通可回溯，重要结论进入相关任务。
7. 保留原生子代理能力。Crew 成员和原生子代理的执行、停止及结果归属能够解释清楚，避免重复组织与层层转述。
8. dispatch 的清晰任务说明、干净上下文和交付依据可融入成员提示词。本轮不另建共享 dispatch 服务。
9. 用户执行中补充要求时，优先用原生支持的中途调整能力交给当前 AI；保留明确的排队发送。请求接收、送达和失败要能区分。
10. 不把“中途回复快”推断成底层必然调用另一模型。按 CC/Codex 实际支持能力实现并显示真实结果。

持续推进必须来自真实执行控制链路。只修改提示词、做一个循环按钮或在界面显示“运行中”，不满足这一部分。

### 任务级全自动开关与拍板

| 情况 | 必须实现的行为 |
| --- | --- |
| 关闭全自动 | 新框架、审美、交互体验和重要取舍由我在原任务对话拍板；其他可做部分继续 |
| 开启全自动 | AI 在本任务目标和约束内自行选择路线、实验及取舍，持续记录结果 |
| 调整任务模式 | 作用于本任务和其成员；保存、载体切换和重启后保留，不扩展为全局授权 |
| 改变目标或明确约束 | 保留原要求，说明变化；不能把全自动理解成可以任意扩大范围 |
| 原生工具权限 | 使用设置中的 CC/Codex 权限配置，与任务决策开关分开 |
| 多个问题待拍板 | 在任务里一起沟通，可以集中回答；已有临时选择不因切页丢失 |
| 首页出现待拍板 | 只给简短摘要并跳转原任务，完整说明与决定留在原对话 |

已确认的有效决定及其适用版本应可追溯。切换为全自动时要按新模式重新判断仍待处理的任务内选择；明确缺失的资料、凭证及必须由人完成的操作仍作为 TODO，不伪造用户输入。

### 停止恢复与故障

1. 对话中的停止只打断当前对话 AI 的当前执行，不连带停止其他成员或整个任务。被打断的同一轮不能立即被恢复逻辑原样重放。
2. 任务有单独停止按钮，停止本任务的 leader、成员、待派发和后续自动推进；不停止其他任务。
3. 停止后保留已有文件和成果。停止、删除与回滚是不同操作。
4. 后台恢复时，原来正在执行的工作能够接续；手动停止、已完成、归档及垃圾箱记录不会自动开跑。
5. 用户完成 TODO 只唤醒仍允许推进的关联任务，不能覆盖手动停止状态。
6. 程序记录执行归属和调度状态，避免重复启动同一工作。崩溃发生在外部副作用之后而状态尚未保存时，先核对结果，不能盲目重做。
7. 停止后的迟到消息可以保留为历史，但不能使任务自动恢复、再次派发或产生重复交付。使用执行身份和状态校验约束这一点。
8. 对同一故障只做少量有依据的恢复尝试。实现一个清楚的小次数默认值和可测试的上限；例如最多 2 次自动恢复，再进入受阻状态。该数值是技术默认值，不要求用户重新拍板。
9. 达到上限后，Crew 程序直接发 QQ/Lark 提醒，包含任务、真实错误摘要和入口。通知不需要再调用 AI 生成或批准。
10. 正常的效果优化实验与同一故障重试分开记录。已成功的步骤不因后续失败被自动重做。
11. 载体故障时，符合任务限制、具备能力的另一载体可接续；记录原因、已做工作和下一步。缺失的能力明确说明，禁止静默降级。
12. 保活、重连和基础恢复由程序处理，运维 AI 只按实际故障需要启动。

### CC 与 Codex 原生能力

1. 两种载体都走真实原生执行链路，支持创建、恢复、发送、停止及事件回传。使用适配器覆盖各自差异，业务任务保持一致。
2. Skill、MCP、项目说明和原生配置沿用相应载体的实际装载机制，不退化为只调用裸模型接口。
3. 展示可核实的配置和能力来源，区分“已配置”“已发现”和“确认本次已加载”。载体未提供加载证据时如实显示，不猜测。
4. 模型及 effort 来自原生发现、原生配置或用户选择；不把本机模型清单写成固定产品目录。无法发现时给出真实原因和明确配置入口。
5. 默认角色偏好可以设置，具体成员由 leader 按任务选择。Sonnet、Terra、Opus 是偏好示例，不是所有机器都必须存在的硬编码名称。
6. 原生会话 ID、Crew 会话和任务之间有明确关联。恢复和切换时保留已有结果，避免重复扣费执行已完成工作。
7. 不承诺 Crew 会话自动出现在官方 CC/Codex 桌面应用列表或能继续同一官方对话。这项完整兼容暂缓；本轮保留真实原生能力。
8. 原生工具的限制、错误和不可用状态对用户可见，不能吞错后悄悄换工具。

### 完整设置与可编辑提示词

设置按“全局默认 → 工作区覆盖 → 单个 AI 覆盖”解析。展示实际值、继承来源、作用范围和生效时机；支持取消覆盖、恢复默认。

必须覆盖角色默认载体、模型、effort、实际执行权限、原生能力来源、连接渠道、远程连接、后台和数据位置，以及现有外观与工具设置。

以下 Crew 注入的行为提示词必须能查看和修改：

- 通用推进、沟通、实验与验证原则。
- leader 理解需求、协调和交付规则。
- 成员施工、上下文与结果反馈规则。
- 个人助手提示词。
- 报告写作及持续更新提示词。
- 摘要、压缩、动态上下文装载和交接提示词。

保存修改历史并支持恢复默认。能查看某个 AI 实际使用的 Crew 提示词内容、版本与来源。设置中编辑的内容必须进入真实执行链路，不能只存起来做展示。

新会话使用新设置。已有会话保留当前配置，用户主动应用修改时明确告知实际生效方式；载体需要下一轮或重开才能应用的内容如实说明，不强制中断正在工作的 AI。

用户明确吩咐“以后都这样”时，助手或 AI 可以修改指定的长期设置并说明范围；单次任务要求留在任务里。Crew 可编辑内容与原生私有系统指令区分，避免承诺修改无法控制的原生内容。

本轮不做原生 Skill/MCP 的完整可视化管理器。PC 可以快速打开实际原配置。运行、构建和测试命令由任务 leader 读项目说明后维护，不增加要求我填写命令的设置表单。

### 个人 TODO 灵感与基础助手

1. 个人事项是一张清单，包含可编辑的 AI 标签、工作区归属和相关任务入口。项目归属是独立字段，不只藏在标签里。
2. 全局可看全部，工作区可筛选本项目；归属未明可以先保存为未分配。
3. 快速输入明确区分“记下来”和“开始聊”。记下来保存原话，允许稍后整理，不强制追问；开始聊进入相关任务或新任务对话。
4. 确实需要我动手的事情由 AI 直接创建 TODO，附简短原因与入口。同一个实际操作被多个任务需要时，合并事项，保留全部关联；相似但不同的操作不能误合并。
5. 新 TODO 通过启用的 QQ/Lark 渠道同步提醒。页面、机器人和助手引用同一个事项 ID，避免各自维护独立待办。
6. 我可以勾选完成并补文字或图片，也能在对话里说完成。相关活跃任务接着推进，已停止任务保持停止；重复完成事件不重复派活。
7. 我说做不了或不想做，leader 找替代办法，涉及重要取舍时遵循该任务模式。
8. 提供固定的基础个人助手入口，可读取 Crew 的项目、任务、TODO、资料与成果，帮我整理日常。使用简单、可编辑的基础提示词。
9. 助手收到明确指令时能创建任务、联系相关 leader、查进度、停止指定任务，以及修改明确指定的设置。通过同一业务入口操作，结果可追溯。
10. 助手可以整理、归档和移入垃圾箱，不能永久清空。按需要读取信息，不把全部项目历史常驻塞入上下文。
11. 深化人格、长期记忆架构和复杂主动行为留出扩展位置、记入后续 TODO，本轮不实现完整人格系统。
12. 日常安排和助手聊，不增加复杂的“今天建议”排程系统，也不额外设计灵感转任务的多阶段状态流。

基础助手提示词可从产品需求中的草案开始，进入上述提示词编辑与版本机制。

### 动态上下文与消息

每次执行按任务装载原始要求、有效决定、当前计划、相关文件、实验结论、验证依据和必要的近期交流。记录来源及适用版本；旧结论被纠正后，不继续当作现行条件注入。

成员只接收本次工作相关内容，需要更多信息时可以检索原始记录。长任务压缩后保留关键决定、未完成工作和来源，不仅保留一句“继续上次任务”。切换载体也使用同样的交接依据。

用户中途发言、成员反馈和 leader 私聊都保留真实来源。避免内部消息互相转发产生无限唤醒。消息重复送达、重连和发送失败能够恢复或解释，不把已收到的用户要求丢掉。

垃圾箱内容不进入常规活动上下文。内部历史检索继续保留，本轮不新增全局全文搜索页面。

### 持续报告文档与成果版本

1. 每个实际执行并交付成果的任务维护一份持续更新的报告。只在有结论、实验、重要取舍或可体验成果时更新相关部分；普通聊天直接回答。
2. 报告第一段直接给结果或当前结论，短段落；多属性内容用表格，有分支的结构用图示，合适的趋势数据用图。复用产品需求中用户给出的文档写作规则。
3. 逐节更新，需要查资料的部分可先放用途清楚的 pending。保留用户编辑，并发更新采用实际版本校验；冲突时保留用户修改及 AI 待应用内容。
4. 外部事实需要实际打开来源，附链接和截至日期。图表使用真实数据，不能手编指标或把动画当作进度测量。
5. 文档能查看 Markdown 格式、图片和报告。网页可以打开，PC 可以快速打开项目文件夹及成果运行位置；手机以文档和网页为主。
6. 文本、截图、图片和一般文件能从对话上传、保存、关联和读取。附件显示真实文件信息和失败原因。读取与下载走已认证、限定归属的链路。
7. 报告更新保留阅读位置；有新成果的任务卡提供认可 UI 中的视觉反馈和版本标记。
8. 每次明确阶段交付显示版本号，关联实际代码、文件或内容对象，以及生成时间和来源任务。原型版本、任务成果版本与 Crew 应用版本分别表达。
9. 可以找到某版本的真实内容并恢复目标效果。Git 项目用可追溯的提交或变更依据；普通文件夹用本轮涉及文件的真实版本快照，不强制 Git。
10. 版本恢复先检查当前文件与目标差异，保留其他任务和用户后续修改。冲突时保留双方内容并说明具体需要处理的文件；禁止整库 reset 或整目录覆盖。
11. 只登记一个 commit/hash/绝对路径，而没有可取得的真实内容，不能算普通文件夹的版本恢复能力。快照与既有文档对象、存储导出机制衔接。
12. 报告完成、天亮或到达汇报时间不会结束未完成任务。达到完成标准后再交付；需要我体验的部分明确显示待体验，反馈继续原任务。

### 独立后台与跨设备网页

1. Crew 后台独立于 Electron 常驻。关闭窗口、退出桌面前端后任务继续；另有明确的后台管理及停止入口，区分“关闭界面”和“停止执行服务”。
2. 桌面和普通浏览器使用同一业务 API 与同一份数据；网页能进入全局首页、工作区、任务、助手、设置和文档，不依赖 Electron preload 才能完成核心操作。
3. 保留既有服务发现、home、后台来源和复用规则，防止多个前端重复启动服务或错误接到另一份空数据。服务位置、源码来源和连接失败清楚可查。
4. 首版采用用户常开电脑执行和保存数据。PC 离线时远程暂不可用可以接受，界面应明确断连。重连后恢复状态，避免重复发送同一操作。
5. 完成个人远程访问方案，优先评估 Cloudflare Tunnel 或相近的低成本方式。实施时核对官方现行条件，不能把免费额度或付费能力当作永久前提。
6. 登录与会话、允许的入口来源、敏感操作校验、文件归属和反向代理信任边界需要真实实现。远程网页可控制完全访问 AI，不能只去掉 Host 限制或裸露本机执行 API。
7. 对话流式连接、长任务状态、附件和文档链接经过远程入口可用；网页刷新、断线重连和任务直达链接保留正确归属。
8. 手机可对话、拍板、处理 TODO、控制任务、切换任务模式、使用设置、打开文档和网页。手机轻量化体现在布局；不增加 PC 专属授权限制。
9. PC 支持完整操作和本地打开目录。普通浏览器无法调用本机目录时，给出真实可用的桌面打开方式或路径，不伪装已经打开。
10. 域名、Cloudflare 账号或凭证缺失时，完成代码、配置入口、配置检查、部署步骤及隔离代理验证，集中列出唯一剩余外部操作。没有实际配置就明确标为未上线，不能以假链接交付。
11. 远程访问不要求云数据库。本轮不为了接手机而强制迁到 D1/PostgreSQL；尊重已有存储演进，云同步与云数据库按原暂缓边界处理。

### QQ Lark 历史与垃圾箱

复用现有 QQ 和 Lark 连接、绑定、通知和可用交互。新增 TODO、需要我处理的阻碍及关键成果能按约定提醒，普通实验进度留在任务和报告。通知定位到正确任务，不把密钥放进链接。

通知结果按渠道记录，成功渠道不会因另一渠道失败而重复发送。程序通知有明确的有限重试和错误状态；机器人凭证缺失显示未配置，不唤醒 AI 代替发通知。

完成、归档与删除分别处理。删除运行中任务先停止其全部执行，再移入可恢复垃圾箱，保留项目文件。恢复只还原记录，明确继续后再执行；永久清空只能由用户手动发起。

既有工作区移除、恢复、改名和目录迁移继续保留。垃圾箱和普通历史在查询、上下文与通知行为上区分清楚。

### UI 的真实接入

由前端 AI 将认可的 UI 成果接入真实业务；你提供对应后端能力、接口和桌面桥接，负责联合核对以下行为。页面展示及交互问题由前端分工修复，服务端问题由你修复，跨层问题先定位归属再修改：

- 首页的短摘要、工作区和任务列表来自实际数据；拍板项跳转原任务。
- 成员状态卡可进入其对话，顶部“任务 → leader → 成员”可逐级返回。
- 任务详情能读写，成员列表反映真实执行，成果展示真实版本和内容。
- 立即发送、排队、停止当前对话、停止任务及全自动开关各自生效。
- 导航保留草稿、阅读位置和所属任务；报告返回后回到原对话对象。
- 设置展示并修改真实有效值，加载、空白、保存中、冲突、失败、断连等状态可理解。
- 手机单栏可操作，输入键盘和文档不会挤坏布局；动画不阻塞点击或制造错误状态。
- 保留既有关系总览、置顶、工作区管理、Git、用量额度、待收编、公共频道及其他已有入口。原型没画的功能逐项安放和核实。
- 深浅主题及减少动画设置可用；复用已有视觉系统和用户认可的动画，不另起一套页面风格。

## 数据迁移要求

迁移须覆盖真实历史，而不只是创建一张新任务表。先核对旧 goals、leader、成员、运行实例、消息、决定、TODO、报告与新存储服务之间的实际读写关系。

1. 保存来源映射和稳定关联。旧目标转成任务后，原消息、交付与入口仍能找到；旧 leader 总会话保留为可访问历史，不能强行全部归到某个新任务。
2. 任务级全自动模式从旧数据有明确迁移依据。不能把 leader 上的一次信任设置扩散到全部历史或新任务；旧值含义不明时保留原值来源并采用解释清楚的保守映射。
3. 迁移不启动旧的停止、归档或已删除执行。新后台恢复逻辑与历史迁移分开。
4. 迁移可重复检查；失败保留真实原因和原数据，不能部分失败后展示空白成功。备份和恢复步骤可执行，在合成旧库上验证。
5. 新旧访问入口过渡期间必须有单一事实来源或明确适配规则，不让 CLI、hooks、网页和后台分别写出两份不同进度。
6. 核对存储导出、导入、历史资料和上下文桥接。新增字段或关联需要进入现有可携带数据链路，设备路径与原生运行 ID 按本地绑定处理。
7. 使用可公开的合成历史样本覆盖旧版、重复运行、失败中断、普通文件夹和多工作区，不读取正式私人数据库充当测试夹具。

## 前后端同步推进

前端与后端由两位 AI 同时施工。你作为后端 AI，兼任接口收拢与最终集成负责人；不需要再等第三位负责人接手。前端可以独立启动、使用模拟数据开发，最终通过真实接口连接同一套 Crew 服务。

| 分工 | 负责内容 | 修改边界 |
| --- | --- | --- |
| 前端 AI | 认可 UI 的组件、布局、动画、PC/手机交互、页面状态、客户端数据适配和模拟数据 | 主要在 `plugin/crew/web/`；桌面首页展示部分先协调现有修改 |
| 后端 AI | 任务领域、存储迁移、执行与恢复、载体、设置、通知、认证、文档与 HTTP/事件接口 | 主要在 `plugin/crew/` 的领域模块、`web_api/` 及相关测试；按模块登记接口，不同时重写前端页面 |
| 集成职责，由后端 AI 兼任 | 接口定义、变更协调、真实联调、桌面桥接、完整验收、构建和合并 | `desktop/src/main.cjs`、`core.cjs`、`preload.cjs` 等跨层文件明确归属后再改 |

你开工先从真实链路整理第一批接口，形成双方共用的接口说明及示例数据，前端据此独立推进；已有前端约定时先核对并衔接。优先从当前 API 演进，避免根据两个 AI 各自的猜测设计两套协议。第一批覆盖工作区/任务列表、任务详情、对话与事件流、两种停止、任务模式、成员和设置；随后按功能补充 TODO、报告、附件与历史。

接口约定至少写清：稳定 ID 与归属、字段类型、状态含义、请求/响应示例、分页或增量规则、错误格式、并发修改版本，以及流式事件的类型、顺序和重连方式。停止当前对话与停止整个任务必须是明确不同的业务操作。需要改接口时先同步说明和相关夹具，再更新两端。

前端通过统一的客户端数据层调用服务，将普通请求、事件订阅、附件访问和桌面专有能力从页面展示中分离。开发时可显式选择模拟实现或真实实现，不在生产断线时偷偷退回假数据。模拟实现使用约定的结构，能够演示加载、错误、断连、等待拍板、停止及并发修改冲突，而不只显示成功页面。

对齐基线后，复用模块指南中的功能所有者、动作登记、渲染与对话工作区能力，再按真实数据调用补适配。避免重新写一个包含全部功能状态与事件的巨大 `app.js`；不要求先整体更换前端框架。桌面首页使用的 `window.crewDesktop` 需提供清楚的能力适配：普通浏览器使用服务 API；打开本地文件夹等操作由桌面桥接或明确的替代入口承担。核心网页业务不能依赖 Electron 全局对象才能运行。

前端可用独立开发服务加代理连接后端；最终也可以由 Crew 服务提供静态页面，保持同源访问。并行开发不要求把生产前端和后端部署到不同站点。

不要等全部后端写完才联调。按“任务列表 → 进入对话 → 发送/流式回复 → 两种停止 → 模式与设置 → TODO/报告/附件”的顺序逐条替换模拟实现。前端交付须能切换到真实接口，后端交付须能由界面实际调用；最终负责人按完整验收矩阵确认集成。

## 实施顺序

下表是施工依赖顺序。可根据现有已完成能力压缩步骤，所有必做内容仍要覆盖。不要按表机械新建模块或为每行强制创建一个 PR。

| 阶段 | 交付结果 | 结束依据 |
| --- | --- | --- |
| 1 现场与复用 | 文件归属、模块化主干基线、已有变更衔接、能力映射、状态与数据契约、UI 接入位置、隔离环境 | 两端使用包含模块化成果的共同基线，保留有效已有工作，再开始增量改造 |
| 2 任务与迁移 | 稳定任务关联、任务模式、旧数据映射、统一访问入口 | 合成历史和新任务均可读写，迁移可恢复 |
| 3 第一条真实流程 | 对话形成任务、假载体连续执行、成员、停止、恢复、阶段成果 | 先由隔离服务 API 跑通；前端可用后追加界面验证，不等待页面才施工 |
| 4 执行与配置 | 双载体适配、完整设置、提示词生效、干净上下文及中途消息 | CC/Codex 契约与配置行为有可复现依据 |
