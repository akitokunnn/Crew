# Crew 新手引导与 Teamwork 作战室产品设计

> 日期：2026-11-27
> 状态：方向已与用户收敛（交互与技术细节待落地时细化）
> 关联基线：分支 `claude/spatial-studio-ui`（`frontend/` 高密度 Spatial Studio 视觉体系）

---

## 1. 已拍板的方向

1. **Teamwork 只有一种形态：跨常驻 Leader 作战室。** 不做“单 Leader 带临时专项分身”：单个 Leader 内部的并行已由任务内执行承担（组员 = 任务里的执行，按任务开、验收后自动归档），不再新增分身或 `teamwork-worker` 之类的角色。
2. **作战室发起者有两种：Leader 或全局助手。**
   - Leader 发起：一个需求横跨多个领域，需要几个常驻 Leader 联合推进。
   - 助手发起：新工作区开局起盘，或后期一次超大作战（整体重整、推翻部分已有结构）。
3. **开局只是作战室的一种用法**：成员是开场时新建的 Leader，不是另一套流程。
4. **作战室复用交流区的消息与投递状态**，不另起一套消息系统。
5. **助手的全部动作来自统一操作清单**：助手能做的事与界面、CLI 完全一致，开局和重整不写专用代码（见第 6 节）。

---

## 2. 首次打开软件：轻量新手引导（Onboarding）

目标是 30–60 秒完成基础就绪，同时让人看出 Crew 和普通单聊工具的区别，不填长表单：

1. **执行载体体检**：自动探测本机已安装并登录的 Claude Code / Codex（后续可扩展其他载体），展示可用状态，选默认大脑和速度档位。
2. **外观与特色一览**：显示模式（跟随系统 / 浅色 / 深色）、字号；简要展示多载体混搭、上下文压缩小环、离开模式远程提醒、拍板与自主推进两种模式。
3. **选择第一个工作区**：打开已有项目文件夹，或新建空白文件夹（普通目录即可，不强制 Git）。

载体探测、外观设置等能力现有代码大多已有，引导页主要是把它们串成一条顺路。

---

## 3. 空白工作区的两条路

进入新的空白工作区时**不强制引导**，两个入口地位平等：

- **路径 A · 自己搭**：直接进工作台，由用户决定何时建第一个 Leader、是否画架构图。
- **路径 B · 助手开局**：由全局助手发起一次开局作战（见 4.2）。用户先在想法墙画的思维导图可以直接作为输入草图，跳过从零问答。

---

## 4. 跨 Leader 作战室

### 4.1 Leader 发起（跨领域联合推进）

- **适用**：需求横跨多个领域（如前端 + 协议网关 + 语音模块联调），单个 Leader 推不动。
- **协作方式**：
  - 牵头 Leader 开启作战室，邀请相关领域的常驻 Leader 进房，替代零散、难追踪的交流区喊话。
  - 房内共享同一份接口契约与任务状态板；每条点名、引用都显示真实投递状态（`仅归档 / 已排队 / 已送达 / 已回复`）。
  - 成员之间直接 `@` 对话，**牵头 Leader 只负责收口，不当中间层转述**。
  - 跨组分歧或关键决策汇总为**一张拍板卡**交给用户，避免多个 Leader 分别打扰。
- **收尾**：验收完成后作战室归档，受邀 Leader 带着这次协作的上下文回到原岗位（不销毁）。

### 4.2 助手发起（开局起盘 / 超大作战）

助手作为总控，把“定结构 + 建制 + 首轮推进”作为一次完整作战，而不只是建几个空壳 Leader。

1. **探底与对齐**
   - 已有代码目录：先派只读调研，摸清目录结构、技术栈、核心模块与现状。
   - 空白目录：用 2–3 个关键问题和用户对齐目标、范围、优先级；有思维导图时直接以它为草稿。
   - 后期重整：读取现有架构图、Leader 编制、进行中的任务与近期交付，找出要调整的部分。
2. **出方案**
   - 开局：项目思路图（领域划分、边界与依赖、各领域推荐载体/模型）+ 首批任务清单。
   - 重整：**改前 / 改后对照**——架构图变化、哪些 Leader 合并 / 拆分 / 退役、哪些任务作废或改派、预计会启动哪些 Leader。
   - 用户可直接增删改，然后确认一次。确认时可选“建完立刻开工”或“先只建结构和团队，暂不启动模型”。
3. **执行**
   - 一次性落地架构图（`domains` / `domain_leaders`）与 Leader 编制，助手把首批任务派给各 Leader 并开工。
4. **首轮交付与交棒**
   - 助手盯完首轮里程碑和跨领域联调，向用户交付可验收的成果，作战室归档，各 Leader 转入日常推进。

### 4.3 助手作战的三条边界

1. **助手只动结构，不直接改代码。** 助手可调整架构图、领域划分、Leader 编制、任务（作废 / 改派）；代码层面的推翻作为任务派给对应 Leader 实施，经正常验收与 Git 助手合入。
2. **先看结构变化再执行，并可回滚。** 方案确认前不做任何批量改动；架构图保存版本，结构层面的推翻可一键回滚到上一版。
3. **被合并或退役的 Leader 不丢上下文。** 复用现有“更换载体”的可编辑交接预览，把上下文交给接手的 Leader，原会话归档保留。

### 4.4 费用控制

- 自动建制并开工前必须经用户确认一次，明确展示新建 / 启动的 Leader 数量、各自载体与模型、首批任务范围。
- 作战室设预算上限：首轮花到设定的 token 量先暂停，等用户确认再继续。

## 5. 作战室界面（Spatial Studio）

无论谁发起，都用同一套高密度视图（适配 `1280px` 桌面、`760px` 窄屏、`375px` 手机）：

- **顶部参战栏**：成员 Leader 头像、实时状态、载体标签、上下文压缩小环，一键暂停 / 人类接管。
- **中间主时间线**：默认折叠细碎工具调用，突出交接节点、阻塞原因、`@` 点名的真实投递状态与待拍板卡；人类随时可插话纠偏。
- **右侧面板**：
  - 开局 / 重整：可编辑的项目思路图（重整时为改前 / 改后对照）与建制、首轮执行进度。
  - 跨领域推进：任务拆解、分支状态与交付物 / 报告预览。

## 6. 底层依赖与落地顺序

### 6.1 底层原则

- **统一操作清单是唯一事实来源。** 每个操作登记名称、参数格式、读 / 写、风险等级与说明；网页界面、CLI、Codex 动态工具、MCP 都只是它的薄适配层，CLI 保留（任何能跑 shell 的载体都能用）。
- **对 AI 只暴露少数通用入口**（例如 `crew_do(action, data)` + 按需查说明的 `crew_help(action)`），不为每个操作单独定义一个工具，避免工具定义撑大上下文。助手操作指南由清单自动生成。
- **能写进后端状态机的规则不写在提示词里**：投递状态由后端判定；写操作必须对应用户真实发出的那条消息；高风险操作（删会话、清理工作区、退役 Leader）需要用户确认。
- **作战室事件走增量事件流**，桌面端与未来手机端订阅同一份事件。

### 6.2 落地顺序

1. **R2 消息投递可靠性**：修复“以为已回复、实际只在排队”、交流区待送点名被跳过、`--reply-to` 不通知原帖作者。作战室依赖这一层可信。
2. **统一操作清单 + 助手完整覆盖 Crew 操作（R5）**：加一条测试，保证界面上每个改数据的动作都在清单里。
3. **跨 Leader 作战室**：在交流区话题的基础上加成员、状态板与拍板卡，先支持 Leader 发起。
4. **助手发起的作战**：开局与重整作为同一功能的两种用法；接入想法墙思维导图（R3）作为输入。
5. **新手引导**：成本最低，可在任意阶段插入。

---

## 7. 待细化的点

1. **交流区与作战室的边界**：交流区保留为轻量异步广播 / 通告；什么程度的讨论应一键升级为作战室，在 R2 重构时一并定。
2. **作战室的范围**：默认限定在单个工作区内；跨工作区作战暂不考虑。
3. **重整的粒度**：哪些结构变化允许一次批量执行，哪些必须逐项确认，在实现 4.3 时细化。
