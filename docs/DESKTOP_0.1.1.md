> 历史记录：下文的版本、运行状态和“当前”均指本次交付当时，不代表现在。当前检出与运行现场请按 [AGENTS.md](../AGENTS.md) 核实。

## 用户要求与实现选择

用户授权在独立分支测试、提交和推送，要求保留运行中的 Crew 任务；后续补充多工作区、完整应用外观、工具更新、文档归档，以及 Git 分支收尾。采用持久项目标签、紧凑文档侧栏和可取消的更新队列。2026-10-24 用户进一步要求使用 claude-dispatch 参考 Claude Opus 5.5 的意见，按 skill 的只读工具白名单下发审查；结果由主控抽查和修复，详见后续审查记录。

## 桌面体验

- 36px 灰色标题栏、Windows 原生最小化/最大化/关闭按钮、可拖动区域、细边框与圆角内容区。工作区首页和项目页面使用同一外壳。
- 工作区首页改为紧凑的文件夹列表，显示名称和路径，支持刷新、打开已有 Git 项目、新建工作区。新建表单支持键盘提交和 Escape。
- 标题栏提供返回、工作区首页与应用菜单。原生菜单支持新建、打开、刷新、关闭到托盘、退出和版本信息；从项目页使用新建/打开也能完成导航。
- 同一窗口可同时打开多个项目标签。项目使用独立的 WebContentsView，各自保留聊天输入、所选 leader 和滚动位置；切换只显示/隐藏原页面，重复打开同项目选中原标签。关闭标签不停止其后台任务。`Ctrl+T` 返回工作区选择器，`Ctrl+Tab` / `Ctrl+Shift+Tab` 切换标签，`Ctrl+W` 关闭当前项目标签；仅剩首页时收起窗口。
- 图标沿用 Crew 网页的开环和独立圆点，制作了 SVG、11 种 PNG 和 7 种尺寸的 Windows ICO。桌面、程序文件、托盘与安装入口使用相同品牌。

## 人工待办、拍板与全部视图

“我的待办”成为有未完成事项时的默认入口，记录要做什么、具体步骤、验证方法和是否卡住 AI。支持完成附备注、取消写原因、撤销和跳到 leader；结果走原通知链，由 leader 安排阻塞成员继续。左栏计数、全部页提示和组内折叠托盘使用同一份数据，QQ `/todo` / `/t` 只提供查询。首次上线由各 leader 盘点仍有效的历史人工事项，不靠关键词猜完成状态。

拍板改为一题一件事，必须讲清为什么需要用户选、建议和理由、每个完整选项的行动及后果；技术背景折叠。旧题保留原文并可要求 leader 原位补写，修订后的旧 QQ 按钮不能误答新版选项。工程安排由 leader 自行决定，亲手操作进待办。“全部”使用每组一列的横排，支持组/成员评论；本轮选择简单横排，没有做无限蓝图画布。完整规则见 [工作流程](WORKFLOWS.md)。

## 文档交付

- 左栏增加文档中心和数量；按标题/摘要/路径搜索、组/类型筛选和只看重要。重要汇总优先，卡片显示摘要、提出者、组、更新时间和来源会话。
- 宽窗口对话右侧使用 220px 本组文档栏，最多五份；窄窗口收为抽屉，不压缩输入框，和架构抽屉互斥。支持直接预览、打开原文件和回到来源 leader，切换保留草稿。
- `crew doc add/list/refresh` 和 Codex 三个同等动态工具。新登记要求标题和摘要，更新同一路径不重复建卡；AI 重要标记与用户星标独立，用户标记优先，可以恢复自动标记。
- 历史聊天中的本地链接与会话报告分批索引，按字节/行数/会话预算推进。不会猜摘要或重要程度；半行追加保留等待，错误可见。文档留在原位置，缺失明确提示。
- document_id 从卡片贯穿解析、预览、打开和显示文件夹，后端查回可信的原提交者；相对资源继续按其工作树解析。ID 失败不退回客户端路径，所有文件入口重新检查项目和真实路径。

## 连接、中断与全局系统管理员

输入区增加明显的“中断”按钮。只向当前 Crew 托管会话发原生中断请求，收到 HTTP ACK 后仍显示等待，直到真实结果/状态确认当前轮结束；空闲会话不重复发，外部会话明确要求回原工具操作。中断保留 native 会话、日志和输入草稿。真实隔离 HTTP + FakeProcess 及 Renderer 四项检查覆盖请求、确认与草稿保留，没有向正式模型发测试。

首次读取聊天失败现在每 3 秒重试；切 leader 或卸载组件时取消，旧请求的结果不会污染新对话。等待历史时可写草稿，避免历史未加载就误发。这个改动针对已复现的旧 UI 缝隙，不把所有连接错误都归因于它。

全局系统管理员是每 Crew home 唯一的独立守护进程，独立于所有 leader，不使用模型，也不接工程任务。顶部和首页均有入口，健康页面直接通过桌面 IPC 读本机记录，后台 HTTP 失联时仍可查看；入口握手不依赖工作区列表成功。它记录健康时间、管理员/后台 PID、自动恢复次数和最近异常。

后台进程确实退出才自动恢复，保留原端口，退避并限制五分钟内的自动恢复次数；活 PID 仅响应异常时标记降级，不强杀模型。请求绑定管理员实例和唯一 receipt，旧实例或重复请求不能误操作新进程。明确退出会停止自有后台并等待真正退出，借用服务不受影响；桌面意外断开时管理员继续监测。维护标记禁止新建或自动恢复服务。手动“尝试恢复”只针对确认已退出的后台，实际结果以快照为准。

恢复前重新读取最新服务登记，发现其他兼容后台时改为借用；未知响应阻止另启。CLI、登录启动和桌面入口共享同一 home 的后台 OS 锁，数据库初始化前取得、进程退出后释放。`crew web --open` 在锁竞争时通过已登记服务的 HTTP 查项目并打开现有页面，不创建第二个后台，也不读取本地数据库。

管理员与后台启动慢时，桌面会显示离线外壳和健康页面，不等待卡住的 Python 退出才能打开窗口。后台迟到就绪后，空工作区首页可重新连接实际端口。管理员状态保留上次后台 PID/地址证据，维护或失败快照不会清掉它；是否已有管理员以实际 OS 锁判断，旧 PID 被复用不会造成假占用。真实延迟启动验收覆盖超时后页面可用、迟到恢复和正常退出。

## 每组信任与成员更换工具

信任设置移到每个 leader 的对话页与菜单，每组独立目标、开关和报告。下属继承本组；绑定 AI 不能修改别组，无绑定的人类 CLI 必须指定 `--leader`。保存只写配置和审计，不产生通知、不启动任何会话。下次正常发送、唤醒、恢复或压缩时，附最新显式开启/关闭说明；关闭会明确覆盖旧授权。旧项目级设置只迁移一次给既有 leader，新 leader 默认关闭。

报告页面汇总已保存的决定、待办、会话报告与交付记录，是供 leader 补齐证据的草稿；它不会自动完成 Git 提交、测试或实机验收，也不把聊天里的完成声明当作验收结果。

拍板按提出时的 leader 固定归属，列表、澄清、答复、QQ 路由和自主决定报告使用同一归属。成员后来换组不转移旧题；原 leader 归档、关闭或其组关闭时暂停自动授权。升级前的历史题只能按迁移当时成员关系保存，不能回溯未知的旧归属。报告中的进展、人工待办和工作区记录按当前成员归属汇总，页面会说明这个范围。

成员卡可选择 CC 或 Codex，展示目标模型/effort、本地交接摘要与用量提示。确认有 5 分钟时效，配置或会话状态变化后需重新审阅；确认只保存工具与交接，不启动模型。当前运行端必须空闲且真正退出，外部会话、未知进程状态、未排空输出和活租约均拒绝。Crew ID、组、任务、工作树、分支保持不变，两端分别保留 native 历史；切回可恢复原绑定。默认模型/档位由运行端决定，恢复旧原生会话可能保留其原设置，需具体覆盖时应明确选择。

交接只在目标接受下一条输入后消费：Claude 核对原生会话 ID 和准确用户消息 UUID，Codex 核对接受的 turn。失败保留交接并显示错误，不偷偷换回另一工具。聊天日志只记录用户原始输入。迟到工具/元数据入口检查当前载体，但它们不能撤回已执行命令，也不区分同类工具的旧 generation，主流程仍必须确认旧进程退出。

独立 Git 项目实际跑了三轮：Claude Sonnet 5.5 → Codex → 原 Claude 会话。随机 marker 经交接保留，Crew UUID 与原 Claude native UUID 不变，Codex 独立 thread 绑定恢复，两个确认步骤均无模型调用；临时 Codex 认证配置结束后删除。真实 UI 的 18 项检查覆盖两组信任隔离、保存无通知/发送/唤醒、配置往返与过期预览；新建另一种历史、启动失败和活进程拒绝另由协议及生命周期测试覆盖。

## 执行工具版本更新

桌面“工具与更新”检查 Claude Code 和 Codex CLI 的当前/最新版本及安装来源。自动更新默认关闭；手动或自动请求都可排队，忙时等待、可取消，安装前再次检查本机相关进程和来源路径。应用退出会等待已开始的安装，不中断安装器。

支持确认过的 npm 安装和 Claude 原生安装。固定 npm registry 和包名、直接执行确定的 node/npm-cli，保留原 prefix；Claude 原生使用 `claude update`。未知安装来源、版本无法读取或进程枚举失败时显示原因，不猜更新命令。版本已相同或更新则不降级。更新使用跨进程锁，记录到 home/desktop/logs/tool-updates.jsonl。

本机只读检查时 Claude 为 2.1.306，注册表最新 2.1.310；Codex 为 0.163.0，最新 0.164.0，两者均有进程占用。本轮未真实安装或替换 CLI，更新成功/失败/排队的自动化验收使用模拟 helper，真实版本查询另行验证。参考 [Claude 官方安装与更新](https://code.claude.com/docs/en/setup)、[Codex 官方 npm 更新说明](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)。

## 现有服务与升级

桌面版优先复用 `web.json` 登记的服务。旧服务只有 `/api/state` 时，按项目补读根目录。没有服务登记，或只读探测明确证明旧后台已退出、端口和 home 锁均空闲时，才允许启动新服务；超时本身不构成重启依据。未知进程、HTTP 错误、损坏登记或不兼容响应会显示错误，避免两个服务共同写一个数据库。

`--service-url` 明确指定服务时必须成功连接，失败不自行创建替代服务。借用服务的窗口退出不会停止该服务。`--profile` 为升级窗口提供独立的界面配置目录，不改变 Crew 数据 home。

不同 profile 同时首次启动也使用同一 home 的系统文件锁；锁在安装入口/数据库初始化之前获取，进程退出或崩溃后由系统释放，保留锁文件以避免删除旧锁时的竞争。竞争进程以约定的 75 状态码退出，不修改运行入口或服务登记，由桌面读取已启动的服务并借用。

旧 `crew start` / 登录自启入口现在也读取该 home 的 `web.json`，不再把桌面版的动态端口误当成服务未启动；地址只接受无凭据的本机 HTTP 根路径，探测拒绝跳转。没有登记时仍兼容默认 47811 端口。

用户随后明确要求 Crew 完全停止，等修复完成再继续。已通过 SQLite backup API 保存停机前和停机后的数据库，记录原会话清单；停止旧桌面拥有者、7122 后台、托管会话与已登记的外部 Crew 成员及其仍存活的子任务。没有按进程名称批量停止其他 Claude/Codex 会话。47811 与 7122 均无监听，旧自启计划保持禁用；正式 home 留有维护标记，所有后续验收均使用独立 home。

旧 Chromium profile 的 Local Storage / Session Storage 已在所有 Crew 窗口退出后备份，再完整复制到新默认 desktop/ui；原始、备份与目标共 10 个文件逐个 SHA256 相同，原文件保留。备份在 `C:/Users/admin/.crew/backups/desktop-profile-before-011-20261024-1630`。独立 Electron 副本用内置协议返回夹具页面，没有监听或连接正式端口，验证原 `http://127.0.0.1:7122` 的 5 份草稿记录可读；当时这些记录没有非空文本或图片，不宣称恢复了未发现的内容。新版启动入口沿用 7122，避免原点变化隔离旧存储。

停止进程不等于取消任务或删除待投递消息。正式后台下次启动后，原有 working journal 和有效通知仍可能按既有机制续跑；本次维护期间没有启动后台来消费它们，也没有改写用户任务状态。

## VS Code 待收编

功能及收编入口始终保留。本机现象是后台状态停留在“还没读到 VS Code 会话列表”，运行中列表仅来自实时进程回退，历史列表为空。只读检查可读取 6 个项目/工作树根目录、69 个会话文件和 73 个隐藏 ID，因此没有发现历史文件丢失。

进一步检查进程发现，当前服务的 `git worktree list --porcelain` 子进程从 13:19 一直停留到 13:45 之后，扫描卡在第一次 Git 查询；原调用没有超时。已加 10 秒超时、关闭 stdin 和 Windows `CREATE_NO_WINDOW`。这确定了当前列表卡住的位置，但没有证明 Git 内部为何等待。

另用自有短命父子进程实证了 Windows 的管道边界：`subprocess.run(capture_output=True, timeout=...)` 超时杀掉父启动器后，仍可能等待后代持有的 stdout/stderr 管道。新扫描优先使用同一标准 Git 安装内的原生 `mingw64`/`mingw32` 可执行文件，并用临时文件捕获输出，使父轮询的超时不再依赖后代关闭管道。未知自定义 Git wrapper 的后代进程清理不在该窄修承诺内。

“不能新建组员”也观察到同类卡点：正式旧进程停留在只读 `git check-ignore`。成员创建前的忽略目录检查现在复用原生 Git 与文件输出捕获，10 秒内给出失败而不无限挂住；真正创建工作树的写操作不强杀超时，避免中途破坏仓库。对应成功、失败、超时和 Windows 父子管道回归已通过；停机后没有为验收在正式组内新开模型成员。

另外复现发现：读取正在追加的半行 JSONL、Git 查询临时失败，或共享轮询中的 SQLite 临时锁冲突，也可能让原后台扫描线程退出。修复后保留上次成功列表、显示读源错误，并在下一次 10 秒轮询重试；共享任务的预期 IO 错误也不会永久停止扫描。

用生产数据库的只读备份创建临时副本，运行新扫描器，当时得到 2 个运行中和 9 个历史待收编会话，归档过滤正常；测试未启动任何模型，也未写生产数据库。这个验证证明新进程可恢复检测。后续用户要求全停，正式旧进程已停止，未把临时副本结果称作正式运行结果。
