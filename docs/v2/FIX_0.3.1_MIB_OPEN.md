# 0.3.1：已有 Crew 身份的文件夹可从新记录开始

用户实际运行 0.3.0 便携版，在“打开文件夹”选择 MIB 时遇到：

> 此目录已有工作区身份，但本机没有对应历史。请先导入工作区包。

只读核对确认，项目目录存在，旧 Crew 的 MIB 登记和 `.crew/workspace.json` 中的身份一致，而 V2 的独立数据库没有该身份。问题在打开流程：把“本 HOME 没有这个身份”直接当成必须导入历史，缺少用户希望的“仅使用现有源码，从全新 V2 记录开始”路径。

## 改动

- 打开带旧身份的文件夹时，允许用户明确选择“从全新 V2 记录开始”。取消不创建记录。
- 新记录使用同一个源码文件夹、独立项目身份与空历史；不导入旧聊天、任务或原生执行，不启动 AI。
- 新的身份保存在 `.crew/workspace-v2.json`，原 `.crew/workspace.json` 保留。再次打开优先读取 V2 身份，不重复建项目或标签。
- 创建前在本 HOME 保存固定身份的创建记录。独立标识写入失败会明确报错，不创建项目；注册或历史构建中断后可明确重试，沿用同一身份，成功后清理创建记录。
- 工作区恢复使用相同的标识选择规则，避免以后恢复包时误读旧版标识。
- 已有本机历史，或者 V2 专用标识对应的历史缺失时，不能用 fresh 请求覆盖历史。

## 验证

- 回归用例在旧提交上失败：独立 HOME 发现旧身份后没有 `can_start_fresh`，无法进入新记录流程。
- Python 存储相关回归：最终 157 项，155 通过、2 项因符号链接权限条件跳过。
- 桌面 Node：180 项全部通过。
- 真实 Electron、HTTP、目录选择与消息框隔离验收：46 项通过；新增 MIB 同类文件夹场景，核对原源码和旧标识字节未变，V2 新身份独立、重开保持同一标签和身份，未启动模型。
- 独立复核发现首次修复在标识写入权限失败时会留下不可重开的记录，已补持久创建记录并复验；故障注入覆盖标识写入失败及注册后中断。双标识目录还完成了真实导出包、复制为新身份、激活及重开验证。最终源码另经只读独立复核，无未解决阻断。
