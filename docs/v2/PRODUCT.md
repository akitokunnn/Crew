# Crew V2 初版约定

本轮讨论的实施依据，记录于 2026-10-29。原始总纲为 `rebuild/test:docs/CREW_PRODUCT_REDESIGN_2026-10-28.md`（`af9f281`）；与本页冲突时以本轮用户明确意见为准。旧实现、旧布局、历史交付记录均不构成完成证据。

## 产品与使用方式

Crew 是用户日常使用的主要入口。工作区用顶部标签切换，同时聚焦一个项目。外部工作区首页保留已有方向；工作区内部以任务、讨论、人工 TODO、待拍板和成果为主页。只有进入 leader、成员或助手后才呈现聊天。

全 Crew 只有一个个人助手。她跨所有工作区工作，不属于任何项目；没有工作区时也能打开。具体项目的新需求开启一个新 leader 对话。leader 自己识别任务、整理验收条件、改名，识别用户执行同意后推进；普通讨论不能凭关键词被程序误启动。leader 可以分工和直接实施，成员不再向下派工。成员可以被直接询问，结果仍回到所属任务。

用户主要不满是交互不顺、助手无响应、执行反复刷屏。必须让发送、排队、运行、等待用户、完成、失败各有真实状态；错误保留输入，重试不重做已成功的动作。任务工作与总对话独立，启动一个任务不暂停其他任务。完成后执行细节折叠，保留结论、耗时与可展开的原始过程。

## 完整功能范围

| 能力 | 初版要求 |
| --- | --- |
| 工作区 | 普通文件夹可用，不强制 Git；顶部多标签保留草稿、阅读位置和运行状态 |
| 全局助手 | 跨项目总览、用户明确要求的跨项目操作、快速记想法，独立于运维管理员 |
| 新讨论 | 用户先说想法；名称可省略，AI 设置沿用用户默认并可临时调整 |
| 任务识别 | leader 根据对话识别目标与执行同意；任务、验收、决定、实验、进度和交付留存 |
| AI 待办 | AI 可执行的工作自动分解并逐项完成，与需要用户动手的 TODO 分开 |
| 派工 | 只有 leader 可派成员；CC、Codex、CLI、HTTP、原生工具均遵守 |
| 对话 | 总对话、各任务与成员独立；工作中仍可接收用户输入，显示真实投递状态 |
| 执行呈现 | 去重、合并过程噪声，结束折叠为结论与耗时，细节可查 |
| 人工 TODO | 多任务关联与去重、完成说明、撤回；手动停止的任务不因 TODO 完成自动唤醒 |
| 拍板 | 任务可选择用户拍板或 AI 自主决策；与原生执行权限分开 |
| 提醒 | 程序生成有意义的完成、失败、待处理通知；有限重试，避免相同状态反复唤醒 |
| 成果 | 真实产出后更新报告，任务内“交付与文档”；不恢复侧栏文档中心 |
| 阶段版本 | 阶段报告不强制结束任务；手动修改保存新稿。成果按明确文件清单留快照，恢复前核对后续修改，保留原版本和恢复记录 |
| 反馈迭代 | 对交付继续提意见，保留历史轮次、需求版本与实验结论 |
| 会话控制 | 停当前回复与停整个任务不同；中断恢复，手动停止保持停止 |
| 原生能力 | CC 与 Codex 都可用；模型、effort、工具与用户设置来自原生发现 |
| Codex 接续 | 优先桌面，同一个 native thread 在两端轮流使用；不要求并发输入 |
| IDE / CC 接续 | IDE 不列为初版重点；CC 没有可靠现成方案时可搁置 |
| 数据恢复 | 回收站恢复记录不自动启动 AI；保留已有历史、版本与来源 |
| 设置 | 全局、工作区和 AI 用途设置；保存不启动执行；提示配置保留来源与历史 |
| 外部联络 | 保留 QQ、飞书等现有入口，轻量移动处理，不以全套移动端为初版前提 |
| Git | 可选能力，普通工作区不被迫初始化仓库 |
| 运维 | 系统管理员独立，后台健康与真实来源可检查，不与个人助手混用 |
| V1 并存 | V2 独立默认 HOME、桌面身份和安装入口；不把迁移旧数据当作体验前提 |
| 交付 | Windows 可安装初版，提交到 `rebuild/v2`；不合入 `main`，不替换正式实例 |

## 两条验收旅程

1. **健身打卡 App**：新工作区 → 新 leader 讨论“我最近打算健身，简单给我一个打卡 App” → AI 明确范围和验收 → 根据真实执行同意开始 → 拆分 AI 待办 → 分工实施 → 验收 → 可体验成果 → 用户反馈进入下一轮。用户不必先填任务表、手工命名或反复点击启动。
2. **流式说话人分段研究**：已有项目新 leader → 保留约束“A 的片段、B 的片段、重叠片段；整段流结束后 400ms 内给出截止结果” → 区分未知技术问题与已证实结论 → 形成实验待办和真实阻塞 → 汇总实验与验收结果。这个例子仅用于工作流测试，不授权修改隔壁 MIB，也不允许把模拟事件写成声纹技术已经达标。

## 工程验收与证据

只使用隔离 HOME、临时目录与假 AI 载体。源码、构建产物、运行服务分别核实。测试覆盖真实 HTTP、CC/Codex 协议、消息去重、权限边界、任务独立性、桌面标签和页面交互。原生 Codex 桌面深链存在官方支持，但协议假载体验收不能冒充真实桌面续聊验收；交付必须单列这一限制。

开源借鉴优先采用原生协议和经验证的模式，不为“整合”整体引入另一个服务栈。Happier / Harnss 的原生会话身份、Cotal 的稳定消息身份和去重是参考方向；许可证不同的项目不直接复制实现。研究来源与最终选型、测试结果另记于验收资料，不混入产品界面。

异常恢复同样属于闭环：新讨论创建结果未知时，先通过宿主记录找回原 leader；无法唯一确定时由用户核实并关联已有讨论，不盲目重放原始需求。原生交接因进程中断而未完成时，保留外部控制门禁和真实原因，由用户显式接回，不自动开始下一轮。
