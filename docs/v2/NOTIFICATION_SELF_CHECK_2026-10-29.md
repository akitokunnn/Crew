# QQ / Lark 通知闭环自检

针对当前 `rebuild/v2` 源码，复用 `notifications.Inbox` 和现有两渠道独立消息表；没有搬入归档的任务通知调度架构。正式 QQ、Lark、Crew 服务均未操作。

## 行为与接口

- 主动通知保留未处理拍板、真实会话/任务错误、明确登记的 leader 阶段报告、已发布任务阶段报告和已收尾任务报告。普通等待状态、内部对话的结束句不再自动外推。用户从 QQ/Lark 发起对话的原渠道答复保持现有流程。
- 人工 TODO 新增提醒使用 `todo:{id}:created`，一条共享 TODO 无论关联几个任务，每个已选择的渠道只发送一次。发送前复查是否仍开放；步骤和确认方式有摘要，完整内容仍在 Crew。
- 新阶段报告读取 `goal_report_publications`，通知标识为 `goal-progress:{report_id}`；草稿不发。最终报告继续使用 `goal-report:{report_id}`，完成、未达标、待验收保留真实结果。
- 两渠道原消息表增加 `attempts`、`next_attempt`、`delivery_json`，保存原始发送内容、接收人指纹和批次关联。迁移保留旧内容、成功/失败状态及消息引用。
- 收到明确平台拒绝时最多自动重试 2 次，即总尝试不超过 3 次；重试等待分别为 5、10 秒。重启不重置次数。某一渠道已成功，不受另一渠道失败影响。
- 网络中断、缺少有效消息 ID 或崩溃时遗留的 sending 状态无法确认是否已经送达，不盲重发。错误保留真实原因。事项已处理、接收人变化或恢复的 archived 历史不重发旧消息。
- 自动重试沿用用户的离开状态和主动通知渠道设置。保存连接设置不发送测试消息；只有明确的测试操作才发送测试。
- `connections` 快照中，每个渠道新增 `delivery={max_retries,receipts}`。回执包含事项、状态、尝试次数、下次时间、平台消息 ID、错误，不返回凭据或保存的完整发送载荷。
- 真实 QQ/Lark 用户答复使用宿主持有的进程内授权标记通过任务决策门禁，保留 `answered_by=qq/lark`。仅把 `actor` 文本设成 qq/lark 不能冒充用户授权。重复入站事件、跨渠道重复答复不会重复唤醒任务。

## 实际验证

- `test_notification_delivery test_notifications test_goal_notifications test_connections test_lark`：最终补入重绑定代际回归后 145 项通过，15.90 秒。
- 补充迁移、归档恢复和任务决策联动后，`test_notification_delivery test_goal_modes_reports`：16 项通过，2.06 秒。
- 专项覆盖共享 TODO、两个渠道一成一败、重启/重复 tick、确定失败的有限重试、未知结果不盲重发、处理或换主人取消重试、阶段/最终报告分开、伪造来源被拒绝、真实重复答复只唤醒一次、旧表并发迁移、新主人代际不重发 portable 历史。
- 重绑定会改变回执代际；测试先复现旧批次仍留在 retry 的问题，再验证按保存的原批次退休，不使用新接收人的事项键误清理。
- 旧测试有两处产品期望随需求更新：普通结束句不再外推，人工 TODO 新增现在需要外推。压缩后的原生输入包含最新行为配置，测试同时检查末尾用户原话和 journal 原始消息，不再要求输入完全等于裸文本。

完整 Python 第二轮验证为 2235 项、690.556 秒，OK（7 项平台条件跳过），没有失败或错误；本通知最终源码在该轮已加载。两轮日志及失败修复记录见 `PYTHON_FINAL_VERIFICATION_2026-10-29.md` 与工作树 `Temp/v2-verification/`，不以专项结果代替全量结果。

所有验证只用临时 HOME、假渠道、假载体并清除继承会话身份；没有正式外发。portable 的多任务关联和归档恢复变更由原生接续协作任务维护并与当前通知标识对齐。
