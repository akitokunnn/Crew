# 工作流程更新

## 起会话与工作区

桌面首页选择已有 Git 文件夹，或新建空目录及 Git 仓库；进入后仍使用原来的项目、leader、组员与白板。新建 leader / 成员时选择 Claude Code 或 Codex。未指定执行工具的成员继承所属 leader；跨工具不继承另一个工具的模型。旧会话默认 Claude，不会把原历史改成 Codex。

```powershell
crew leader start --name 感知 --task "交付感知模块" --runtime codex
crew spawn --name 检查 --group 感知 --task "检查接口并报告" --runtime claude
# 以下两条由已加入 Crew 的成员或 leader 会话执行，使用它自己的会话身份：
crew send 感知 "检查完成，接口一致" --kind result
crew wake 感知 "需要处理本组交接"
```

成员现在可以叫醒自己的 leader。叫醒通知会排队等 leader 空闲；不能叫醒其他组的 leader。原有 leader 的跨组协调权限保持不变。

混合工具消息使用 `crew send`；Codex 另有同等的 `crew_send_message` 动态工具。消息绑定 Crew 身份，需要对方行动时明确指定 `--kind task|result|blocker|decision`（原生工具使用 `kind`）；默认 `information` 和 `ack` 只归档、不投递或唤醒。执行消息忙时排队，空闲后投递；外部 Claude 会话通过下一次 hook 收取。回执区分仅归档、已排队与已交给执行输入；最后一种仍不代表模型已读或任务完成。同一次重试保留 `--message-id`，相同编号不能换内容或类型。原生 Claude `SendMessage` 不负责寻址 Codex。

总对话是 leader 的协调与验收入口，任务执行分别保存原生历史并可并行。启动或暂停一个任务不停止总对话或其他任务；总对话消息与中断只属于总对话，向任务输入须明确任务 ID，程序不猜收件任务。组员可以承担多个任务，leader 从总对话分配并按任务验收结果。只有替换同一任务的旧执行代次时才停止旧进程；全体停止仍使用“停止此人”。意外退出保留真实错误与 stderr，浏览器暂时断线不结束仍在运行的工具。

交付、待验收或退回修改之后，任务卡仍可直接输入，继续讨论报告或补充收尾要求。发送新消息才在原任务中继续一轮，带上上一轮交付摘要、产物位置、验收修改意见和先前有效的用户约束。旧报告保持原文，退回理由按轮次保留；打开任务或读取报告不启动 AI。手动暂停和已取消的任务继续要求明确恢复或重开，内部排队消息不能代替用户发起新一轮。

Windows 安装生成原生 `crew.exe` 入口，PowerShell 多行参数不再经过 `cmd.exe`。Windows PowerShell 5.1 自身仍可能改写原生参数中的 ASCII 引号；需要逐字保留正文时，使用 Codex 的结构化 `crew_send_message`，或把正文存为 UTF-8 文件再发送：

```powershell
crew send 文档施工 --text-file C:\Temp\拍板.txt --kind decision --message-id agents-decision-1
```

## 拍板只留真正要用户选择的事

先判断这件事属于哪种流程：

- 工程排程、实现细节和已授权目标中的方案，由 leader 自行判断并汇报。
- 需要用户亲自操作的事，登记人工待办。
- 用户偏好或需要用户决定的取舍，登记一张只讨论一件事的拍板卡。

原截图混合了已完成进展、技术债、待开工列表和组员排程。用户并没有得到一个清楚的问题。类似“继续①和②”不能独立表达行动和后果，应由 leader 整理分类；若真正需要用户先测 develop，就登记具体的验收待办。

新的结构化卡片按顺序显示短标题、为什么需要用户决定、建议及理由、每个完整行动选项的后果。技术背景默认折叠。简写序号和没有含义的 A/B 不能作为结构化选项。CLI 示例：

```powershell
crew ask "是否本周发布已验证的版本？" --title "是否安排本周发布？" --why-user "发布时间影响客户安排，需要你的决定。" --recommend-reason "建议先留一天验收，降低返工成本。" --option "本周立即发布" --consequence "客户本周使用新版本。" --option "等用户验收后发布" --consequence "上线延后一天，先完成验收。" --recommend "等用户验收后发布"
```

旧卡保留原文，不自动推测用户的业务意思；显示缺少说明，并提供“让 leader 说明白”。首次上线会给没有摘要的旧题登记一次补写通知。leader 用 `crew decision revise <id>` 原位补写，同一个题号不重复登记。QQ 旧按钮也绑定原题快照；修订后点击旧选项会要求刷新，避免把旧 A 当成新 A。

为兼容现有会话，旧格式 `crew ask` 仍可调用，但会提示补全说明，卡片也会标记不完整。守则要求新增问题提供完整结构。

## 我的待办

凡是要用户亲手做的事情，AI 登记要做什么、在哪做/怎么做、做完怎么确认，并标记是否卡住 AI：

```powershell
crew todo add "验收舱体动作" --steps "在测试舱体打开验收关卡，按说明走一遍动作。" --verify "人物响应和验收清单一致，记录异常动作。" --blocking
crew todo list
crew todo withdraw 12 --reason "已找到替代验证方法，不再需要用户操作"
```

左栏“我的待办”显示未处理数字。首次打开项目且没有指定页面时，有待办就优先进入此页；明确的对话链接仍打开相应对话。阻塞项在前，显示“卡着 XX”；其余按优先 leader 级别和时间排列。

卡片显示事项、组与提出者、登记时间，展开查看步骤和确认方法。“做完了”可写备注；“不做了”须写原因；“去问它”进入所属 leader 对话。操作后可撤销，版本检查防止覆盖后续改动。全部页显示待办总数，leader 对话托盘折叠显示本组待办。

处理结果走拍板答复使用的 leader 通知链，包含原提出者与备注。阻塞项完成后由 leader 叫醒原会话继续，由 AI 重新验证结果。用户点完成不等于 AI 已通过验收。撤销会删除尚未投递的过期通知，或发更正通知。

首次上线只给每个现有 leader 发一次盘点通知，让它登记以前仍未完成的人工事项；Crew 不猜测旧聊天中哪件事已做过。QQ `/todo`（`/t`）可查看列表，离开电脑时不主动推人工待办。

## 信任模式

在 leader 对话头部或菜单里，只为这个 leader 启用信任模式并填写目标；成员继承所属 leader。用户在普通终端操作时必须明确指定 leader：

```powershell
crew trust set on --leader 感知 --goal "完成感知组目标，验证并保留可修改的提交"
crew trust status --leader 感知
crew trust report --leader 感知
crew trust set off --leader 感知
```

模式只作用于这个 leader 组，不修改全局模型权限。各组目标和开关独立；leader 和成员围绕目标自行选择、执行并验证。登记决定时须给推荐和理由，Crew 将推荐记录为自主答复；没有建议就拒绝自动选项。需要用户亲手操作仍登记待办。

开启、修改目标和关闭只保存设置，不发送通知、不唤醒会话；界面提示“已保存，下次对话会告知它”。无需为了传达设置而额外发送消息。下一次正常对话、恢复或压缩后的上下文会明确传达本组最新开关和目标，关闭也覆盖旧授权。历史决定与报告继续保留。报告只汇总本组，最终需列实现、取舍、实际验证与产物、未验证部分、遗留项、人工待办、commit SHA / 分支 / worktree 和后续修改入口。

升级时，旧项目设置只迁移给当时已有的 leader 一次；后来新建的 leader 默认普通模式。旧待投递的信任通知按原审计事件精确清除，避免升级后被旧队列唤醒。

“查看详细报告”和“下载报告”汇总已保存的决定、待办、会话报告及交付记录，属于报告草稿。它不会自动跑 Git、测试或实机验收，负责的 leader 必须补齐具体证据与实际提交。

## 成员更换执行工具

成员卡片或菜单中的“更换…”支持 Claude Code 与 Codex 往返。正在工作、压缩中、外部 VS Code/终端仍在线或进程状态无法确认时不可切换；Crew 不关闭外部会话。

先选择目标工具及兼容的模型、effort，再查看可编辑的交接上下文和字符数。旧原生历史保留，各工具继续自己的历史；交接包含任务卡、未决事项、文档和有限的近期聊天，并不把历史里的完成声明当验收结果。编辑交接后须重新预览；状态改变或预览过期会要求重新检查。

确认只配置切换，结束空闲的自有进程，不自动开始模型轮次。下次发消息或唤醒才启动目标工具并读取交接，可能增加上下文用量；不编造 token 数或金额。首次使用目标工具新建原生会话，换回已有工具恢复原历史。目标启动失败会显示错误并保留待交接记录，不偷偷回退或重建另一段历史。

## 全部与远程交互

“全部”改为每组一列的横排布局，可横向滚动，组内仍按 leader → 成员显示。组和成员可添加评论；评论按项目保存并通知所属 leader，用户可在原上下文追问。本轮采用简单横排，没有加入无限蓝图画布和拖动连线。

QQ 使用 `/projects`、`/project 项目名` 选项目，再用 `/leader 名称` 选人；`/where` 确认目标。既有 `/1` 等稳定编号仍可用。引用旧消息会回到原 leader，不改变普通聊天的选择。具体行为及 Lark 后续接入设计见 [REMOTE_CHANNELS.md](REMOTE_CHANNELS.md)；Lark 尚未配置收发链路。

## 文档交付与查找

AI 把交付文档保存在项目或自己的 worktree 内，登记标题、摘要和类型；真正值得用户优先读的汇总才标重要：

```powershell
crew doc add docs/交付报告.md --title "感知模块交付汇总" --summary "已完成接口统一；包含验证结果、提交和剩余实机验收步骤。" --kind summary --important
crew doc list --leader 感知
crew doc refresh
```

标题和摘要必填。Codex 也可用 `crew_doc_add`、`crew_doc_list`、`crew_doc_refresh` 原生工具，身份和项目由运行端绑定。重复登记同一路径更新原卡片，不重复复制文件；用户手动设置的重要标记优先于 AI，以后可恢复自动标记。

左栏“文档”汇总本项目交付，支持搜索、分组、类型和重要筛选，重要汇总优先显示。卡片包含提交者、摘要、更新时间、预览/打开入口和来源会话。对话右侧在宽窗口显示 220px 的本组文档栏，最多五份；窄窗口用“文档”按钮打开抽屉。架构图和文档抽屉各有入口。

旧聊天里的本地 Markdown 链接和会话报告会分批整理，不推测缺失的摘要或重要程度；界面提示未填写摘要。历史很多时显示“继续读取历史文档”，重复整理不会重复建卡。文件仍保存在原位置，移动/删除会显示不可用；每次访问都会重新核验所属项目和 worktree，文档 ID 不会放宽文件访问范围。

## 桌面工作区和工具更新

桌面顶部每个项目一个标签，切换保留输入草稿、对话选择和滚动位置。`Ctrl+T` 回首页选择项目，`Ctrl+Tab` / `Ctrl+Shift+Tab` 切换，`Ctrl+W` 关闭项目标签；关闭标签不停止会话，退出应用才停止自己拥有的后台服务。

首页和应用菜单均有“工具与更新”。检查显示 Claude Code 与 Codex CLI 的安装版本、最新版本、来源和占用情况。支持确认过的 npm 安装和 Claude 原生安装；未知来源显示手动处理说明。忙时可以排队，排队可取消；真正安装前会重新核查进程和安装路径。自动更新默认关闭，开启后也遵守空闲检查。更新日志保存在 `~/.crew/desktop/logs/tool-updates.jsonl`。

## 后台异常、维护与恢复（桌面 0.1.1）

桌面标题栏或首页左栏的“系统管理员”覆盖所有工作区，不用另起 leader，也不会启动模型。工作区连接失败、后台启动失败或启动超时时，仍可打开管理员查看本机记录。

1. 先看后台状态、最近检测时间和异常记录。仅对话记录暂时读取失败时，等待自动重试；可以继续写草稿，恢复前不发送。切换 leader 会取消原对话的重试。
2. 需要确认状态时点“重新检测”。“已请求检测”表示请求已接收，完成后的实际结果和拒绝原因由后续状态更新显示。后台仍存活但无响应时，不强制重启以免中断正在工作的会话。
3. 管理员确认后台已退出且允许恢复时，点“尝试恢复”，再等待实际状态。连续崩溃暂停自动恢复时先看异常原因；没有明确允许就不能恢复。后台延迟就绪后，管理员会重新识别连接；回首页刷新列表，再打开工作区即可继续。
4. 显示“维护中 / 已暂停”时保持停止，恢复按钮禁用；维护标记不会因打开窗口或点检测而被清除。按维护安排完成修复后再恢复运行，不能把打开管理员页面当成后台已重启。

最近异常与恢复记录用于定位连接问题；“尝试恢复”不验证工程交付，也不替任何项目做业务决策。

## 中断当前回复

leader 正在回复时，输入区发送按钮旁显示“中断”。对于 Crew 托管的会话，点一次后等待“正在中断”结束；只有实际状态确认空闲后，页面才提示“本轮已停止，会话和草稿已保留”。请求失败时按提示重试，不能把请求回执当成已经停下。

中断只停这一轮，保留原会话、历史与未发送草稿；之后仍可在同一对话继续。在 VS Code 或终端工作的外部会话须去原工具中断，Crew 会说明原因。无需归档成员、关闭工作区标签或停止整个后台。
