# 工作流程更新

## 起会话与工作区

桌面首页选择已有 Git 文件夹，或新建空目录及 Git 仓库；进入后仍使用原来的项目、leader、组员与白板。新建 leader / 成员时选择 Claude Code 或 Codex。未指定执行工具的成员继承所属 leader；跨工具不继承另一个工具的模型。旧会话默认 Claude，不会把原历史改成 Codex。

```powershell
crew leader start --name 感知 --task "交付感知模块" --runtime codex
crew spawn --name 检查 --group 感知 --task "检查接口并报告" --runtime claude
# 以下两条由已加入 Crew 的成员或 leader 会话执行，使用它自己的会话身份：
crew send 感知 "检查完成，接口一致"
crew wake 感知 "需要处理本组交接"
```

成员现在可以叫醒自己的 leader。叫醒通知会排队等 leader 空闲；不能叫醒其他组的 leader。原有 leader 的跨组协调权限保持不变。

混合工具消息使用 `crew send`；Codex 另有同等的 `crew_send_message` 动态工具。消息绑定 Crew 身份，忙时保存在数据库，空闲后投递；外部 Claude 会话通过下一次 hook 收取。原生 Claude `SendMessage` 不负责寻址 Codex。

## 拍板只留真正要用户选择的事

先判断这件事属于哪种流程：

- 工程排程、实现细节和已授权目标中的方案，由 leader 自行判断并汇报。
- 需要用户亲自操作的事，登记人工待办。
- 用户偏好或需要用户决定的取舍，登记一张只讨论一件事的拍板卡。

原截图混合了已完成进展、技术债、待开工列表和组员排程。用户并没有得到一个清楚的问题。类似“继续①和②”不能独立表达行动和后果，应由 leader 整理分类；若真正需要用户先测 develop，就登记具体的验收待办。

新的结构化卡片按顺序显示短标题、为什么需要用户决定、建议及理由、每个完整行动选项的后果。技术背景默认折叠。简写序号和没有含义的 A/B 不能作为结构化选项。CLI 示例：

```powershell
crew ask "是否本周发布已验证的版本？" --title "是否安排本周发布？" --why-user "发布时间影响客户安排，需要你的决定。" --recommend-reason "建议先留一天验收，降低返工成本。" --option "本周立即发布" --consequence "客户本周使用新版本。" --option "等用户验收后发布" --consequence "上线延后一天，先完成验收。" --recommend "等用户验收后发布"
```

旧卡保留原文，不自动推测用户的业务意思；显示缺少说明，并提供“让 leader 说明白”。首次上线会给没有摘要的旧题登记一次补写通知。leader 用 `crew decision revise <id>` 原位补写，同一个题号不重复登记。QQ 旧按钮也绑定原题快照；修订后点击旧选项会要求刷新，避免把旧 A 当成新 A。

为兼容现有会话，旧格式 `crew ask` 仍可调用，但会提示补全说明，卡片也会标记不完整。守则要求新增问题提供完整结构。

## 我的待办

凡是要用户亲手做的事情，AI 登记要做什么、在哪做/怎么做、做完怎么确认，并标记是否卡住 AI：

```powershell
crew todo add "验收舱体动作" --steps "在测试舱体打开验收关卡，按说明走一遍动作。" --verify "人物响应和验收清单一致，记录异常动作。" --blocking
crew todo list
crew todo withdraw 12 --reason "已找到替代验证方法，不再需要用户操作"
```

左栏“我的待办”显示未处理数字。首次打开项目且没有指定页面时，有待办就优先进入此页；明确的对话链接仍打开相应对话。阻塞项在前，显示“卡着 XX”；其余按优先 leader 级别和时间排列。

卡片显示事项、组与提出者、登记时间，展开查看步骤和确认方法。“做完了”可写备注；“不做了”须写原因；“去问它”进入所属 leader 对话。操作后可撤销，版本检查防止覆盖后续改动。全部页显示待办总数，leader 对话托盘折叠显示本组待办。

处理结果走拍板答复使用的 leader 通知链，包含原提出者与备注。阻塞项完成后由 leader 叫醒原会话继续，由 AI 重新验证结果。用户点完成不等于 AI 已通过验收。撤销会删除尚未投递的过期通知，或发更正通知。

首次上线只给每个现有 leader 发一次盘点通知，让它登记以前仍未完成的人工事项；Crew 不猜测旧聊天中哪件事已做过。QQ `/todo`（`/t`）可查看列表，离开电脑时不主动推人工待办。

## 信任模式

网页设置里为本项目启用信任模式并填写目标，也可由用户在 CLI 执行：

```powershell
crew trust set on --goal "完成本项目目标，验证并保留可修改的提交"
crew trust status
crew trust report
crew trust set off
```

模式只作用于该项目的工作流程，不修改全局模型权限。leader 和成员围绕目标自行选择、执行并验证；登记决定时必须给出明确推荐和理由，Crew 将推荐记录为自主答复。没有建议就拒绝自动选项，不默认选第一项。需要用户亲手操作仍登记待办。

开启、修改目标和关闭会通知当前 leader，后续轮次也附当前模式说明。历史决定与报告继续保留。最终报告需列出目标对应的实现、取舍、实际验证与产物、未验证部分、遗留项、人工待办、commit SHA / 分支 / worktree 和后续修改入口。

“查看详细报告”和“下载报告”汇总已保存的决定、待办、会话报告及交付记录，属于报告草稿。它不会自动跑 Git、测试或实机验收，负责的 leader 必须补齐具体证据与实际提交。

## 全部与远程交互

“全部”改为每组一列的横排布局，可横向滚动，组内仍按 leader → 成员显示。组和成员可添加评论；评论按项目保存并通知所属 leader，用户可在原上下文追问。本轮采用简单横排，没有加入无限蓝图画布和拖动连线。

QQ 使用 `/projects`、`/project 项目名` 选项目，再用 `/leader 名称` 选人；`/where` 确认目标。既有 `/1` 等稳定编号仍可用。引用旧消息会回到原 leader，不改变普通聊天的选择。具体行为及 Lark 后续接入设计见 [REMOTE_CHANNELS.md](REMOTE_CHANNELS.md)；Lark 尚未配置收发链路。
