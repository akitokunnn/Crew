# Git 一步到位

用户只说哪些内容测过、可以进主干，其余由你一次做完。做完后本地主干与远端主干指向同一提交，并且包含用户确认的全部内容；未验收的内容留在原分支。

## 开始前

- **先确认是不是在 Crew 里。** 运行 `crew whoami`（Codex 用 `crew_whoami`）：能显示你的 Crew 名字和角色，才算在 Crew 里。命令不存在、报错，或者提示会话未登记、目录未启用 Crew，都算不在 Crew 里：这时没有 Git 助手这一层，由你按项目文档直接完成全部步骤。
- **找主干和集成分支。** 在 Crew 里用 `crew git status`：base 是主干，integration 是本地集成分支（比如 live、dev_live）。不在 Crew 里就读项目的 AGENTS.md、CLAUDE.md 和贡献文档；仍然确定不了就问用户。
- **在 Crew 里，只有 Git 助手能推送和合并。** 如果你在 Crew 里但不是 Git 助手，先完成第 1 步，再用 `crew git request` 把锁定的范围交给 Git 助手（Codex 用 `crew_git(action="request")`），告诉用户已经转交，然后停在这里。
- 项目规定主干必须走 PR 的，第 4 步按 PR 流程走：推功能分支，开 PR，CI 通过后合并，再把本地主干快进到 `origin/<主干>`。
- 始终禁止：force push、改写已推送的历史、删除未合并的分支、推送本地集成分支、合入或推送发版分支（比如 master）。确实需要这些操作时，先问用户。

## 1. 锁定验收范围

逐项写下用户确认的内容：分支、对应提交，以及实际测试包的构建 SHA。范围按用户实际测过的提交锁定，不按分支当前的最新提交：测试包打完以后才追加的提交，留到下一轮。如果说不清用户测的是哪个版本，就问用户，不要猜。

## 2. 整理本地主干

这一步默认不停下来，处理完直接进入第 3 步。只有一种情况要先问用户：**未提交**的有价值修改，会被这次更新覆盖或与之冲突。本地独有提交不属于这种情况：它们已经提交，不会丢，有冲突在第 3 步处理。判断是否重叠时，用命令结果对比文件名（`git status --short` 列出的文件，和 `git diff --name-only <主干> origin/<主干>`、`git diff --name-only <主干> <锁定的提交>` 列出的文件），不要凭印象。

到主干所在的工作区（通常是用户的主工作区），检查两类内容：

- 未提交的修改：`git status`。
- 只在本地、远端没有的提交：`git log origin/<主干>..<主干>`。

编译产物、缓存、日志等可以重新生成的内容，你自己处理，比如 Intermediate、Binaries、DerivedDataCache、dist、node_modules 等目录。

有价值的修改，包括源码、资产、配置和文档，要先看清具体差异，再处理：

- 与这次要更新的文件不重叠的，原地保留。不要提交、还原或覆盖，在最后的结果里列出来。
- 会被合并或快进覆盖、会发生冲突的，先停下来。向用户说明差异，给出保留方案（比如提交到单独的分支，或者存一个有名字的 stash），等用户决定。

本地主干上的独有提交属于用户自己的工作，直接一起带上，不用问，在结果里列出即可。

## 3. 同步远端主干

运行 `git fetch origin`，把 `origin/<主干>` 和本地主干上的独有提交整合到一起。能快进时就快进；不能快进时用 merge，不要 rebase 已经存在的提交。纯机械的冲突（格式、相邻行、两边改动互不影响）由你自己解决。涉及行为取舍的冲突，说明两边各改了什么，再问用户。

## 4. 合入、验证、推送

1. 在自己的 worktree 里，基于第 3 步的结果建一个临时分支，逐个合入第 1 步锁定的提交。按提交 SHA 合入，不按分支名合入，并且保留主干上的最新改动。
2. 按项目文档运行对应的构建和测试。范围覆盖这次合入的改动，不跑和改动无关的全套检查。失败了先查原因：属于合入引起的，修复后复验；属于功能本身的问题，停下来告诉用户，不要带着失败推送。
3. 验证通过后，到主干所在的工作区执行 `git merge --ff-only <结果提交>`，再运行 `git push origin <主干>`。快进被拒绝时（未提交的文件和要更新的文件冲突、文件被编辑器锁住，或者本地主干分叉），停下来告诉用户卡在哪里，需要用户做什么。

## 5. 核对最终结果

- 运行 `git fetch origin`，确认 `git rev-parse <主干>` 与 `git rev-parse origin/<主干>` 输出相同。
- 对第 1 步的每个提交，运行 `git merge-base --is-ancestor <SHA> <主干>`，逐个确认已经包含在主干里。
- 找出仍未验收的内容，包括集成分支上 `git log <主干>..<集成分支>` 列出的提交，以及没有确认的分支，让它们留在各自的分支上。如果还需要继续联测，在新的主干上按范围重新组装集成分支：只合入仍在测试的分支。集成分支上有不属于任何分支的独有提交时，先问用户。
- 清理这次建的临时分支和 worktree。

## 最后给用户的结果

用几行说清楚：

- **主干**：`<主干>` = `<SHA>`，本地与远端一致。
- **已包含**：每个功能或分支，以及对应的 SHA。
- **仍待测**：留在哪些分支，有哪些提交。
- **验证**：运行了哪些构建和测试，结果如何。
- **保留的本地修改**：哪些文件或提交，保留在哪里，还有哪些事需要用户决定。
