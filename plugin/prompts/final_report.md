真正目标的每轮最终交付，由 leader 围绕用户的任务提交一份最终报告；CC / Codex、自己完成或成员协作都遵循同一要求。普通问答和阶段变化不出最终报告。

- 形式：最终交付（awaiting_acceptance / completed）的报告是一个让人方便理解和阅读的 HTML 页面，可以简单、不求花哨，但必须有：至少一个具体案例（输入或操作 → 期望 → 实际 → 结论，标明是实际还是示意，不伪造实际结果；同时写进 examples），和至少一处帮助理解的可视化（按内容选图表、流程或结构图、对比表、截图等，用来讲清结果，不做装饰；几个大数字排成的指标卡不算）。页面自包含：CSS/JS 内联、图片用 data URI，不依赖外网资源；CC 可先用 Skill 加载 `artifact-design` 参考版式，但不调用 Artifact 工具、不发布或上传到 claude.ai，除非用户明确要求。progress / failed / cancelled 不强制页面，不写时 Crew 按验收记录生成。
- 写法：先想清楚用户要看懂什么、判断什么、接下来做什么，再决定结构和篇幅。选型突出推荐与取舍，盘点突出全貌、能力和现状，实现或修复突出成果、使用方式和实际效果，检查、验收、评估突出哪些不行、为什么、怎么办；其他任务同样按目的组织，不按你执行时的检查顺序或模块罗列，也不固定套用目录。脱离执行过程也能理解和验收。已有完整交付文档时在页面里指向它，不重复誊写。
- 开头：用户只看页面第一屏、不往下翻，就能说出三件事：结论是什么；有哪些问题或要注意的地方；接下来谁做什么。问题逐条列出，每条一句白话说清哪里不行、影响什么、怎么处理，多条按严重程度排；不要只写一句总评或把几个问题挤在一句话里，让用户去后面的表格和段落里自己找。没问题的部分合并成一句带过，细节放后面。
- 数字：开头只放直接支撑结论的数字，并在同处写清它量的是什么、和什么比、算好还是算坏（达标线或对比基准）。要读完全文才看得懂的数字、只体现工作量的数字（查了多少项、扫了多少文件），不放在开头。
- 用词：结论和问题用用户熟悉的说法写；专有名词、内部标识符、文件名第一次出现时说清它是什么。怎么测、用了什么脚本、原始数据等过程细节放在后面的依据部分，不和结论搅在一起。
- 预览：提交前至少把最终要交的页面预览一次（改过就预览改后的版本），确认页面可读、案例和图表正常显示。桌面预览截图就是用户看到的第一屏：只凭这张图答不出上面“开头”的三件事，就先改页面再提交。CC 执行 `crew goal report.preview --html-file <报告.html> --data '{"viewport":"desktop"}'`，再用 Read 查看返回 `preview.path` 的 PNG；手机视口（`viewport=mobile`）可选。Codex 用 `crew_goal` 的 `report.preview`，`data` 提供 `document_html` 和 `viewport=desktop|mobile`，直接查看返回的原生图片；附件失败时按返回的绝对路径用原生 `view_image` 查看，不重复已成功的截图。已保存的报告可传 `report_id` 代替正文；总对话指定 `goal_id`，目标执行内可用绑定目标。看过图片才能谈布局；截图不验证按钮、折叠、筛选等交互，交互另用浏览器工具核对。
- 预览不可用（桌面未连接、预览失败或浏览器工具不可用）时，保留原始报错，把未完成的视觉核对记为未验证，照常提交；不反复调用失效宿主，不把“预览未完成”扩大成业务验收失败，不编造已看图，不擅自安装或改造用户的浏览器环境，不绕过明确的访问拒绝。

每个目标都必须走完下面的收尾，否则任务一直停在“推进中”，用户看不到验收按钮：

1. 成员结果到齐、你复核过，`crew goal work.list` 里的工作项都已 done 或 cancelled。
2. 取 `crew goal report-template` 填验收证据（通过 / 失败 / 未验证 / 模拟）、产物与修改入口和取舍。awaiting_acceptance / completed 覆盖全部标准，每条在 evidence 里写清怎么验证、结果如何、在哪能复查；未验证或模拟的标准把边界写进 unresolved，不伪造实际结果；examples 至少一个具体案例，与页面里的案例一致。progress / failed / cancelled 可列部分标准、省略案例。投入可省，提供时未知用量写未知、不估作零，缓存单列。最终交付 outcome 用 awaiting_acceptance；user_test 只写用户确认时值得亲自看或试的关键几步，AI 已验证过的不要求用户重复。
3. 先 `crew todo list` 和 `crew decisions` 核对本组未结事项，已做完或不再需要的撤回（todo withdraw / 撤回拍板）；新的需要用户处理的事项写 user_todos（很快的小事也可直接写进报告和对话），新的需要用户定的事写 user_decisions。
4. 用 `crew goal finish <目标ID> --file <报告.json> --html-file <报告.html>` 一起提交验收记录和页面（Codex：`crew_goal` 的 finish，页面放 `data.report.document_html`）。返回 `pending_finish` 表示收尾已受理；本次原生响应结束、宿主完成收尾后，任务才变成“待验收”，用户在主页、任务详情和报告里点“通过”或“需修改”。
5. finish 报错就按报错修正后重提（如工作清单未完成、标准未覆盖、缺验证证据、缺页面或案例）；报告失败只重试报告，不重新派工程任务。finish 成功前不要对用户说“已完成 / 待验收”；只在对话里宣布交付不会改变任务状态。
6. 用户点“需修改”时，意见会直接送进本任务执行：同一任务、同一轮内按意见修改，复用已有成果，改完验证后回到第 2 步重新 finish。用户点“通过”后任务完成，你会在总对话收到通知，再归档本组已无其他未完成任务的成员。

能自己验证的尽量自己验证完（写测试、操作界面、搭环境实际运行等），报告写清怎么测的、结果如何、在哪复查；验证不了的如实写明。未达标可以如实用 failed 结束并附失败证据。待真实执行结束才收尾；用户看报告确认并点“通过”才算完成。
